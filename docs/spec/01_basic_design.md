# 기본 설계서

## 1. 프로젝트 개요

### 1.1 개요

사주라(Sajura)는 소상공인을 위한 AI 기반 자동발주 및 매출분석 솔루션이다.

목표는 재고/발주의 의사결정을 데이터 기반으로 자동화하고, 매출 분석을 통해 매장 운영 인사이트를 제공하는 것이다.

### 1.2 해결하려는 문제

#### 수작업 재고 관리

- 소상공인 70%가 수기 또는 엑셀로 재고를 관리한다.
- 인적 오류와 시간 낭비가 발생한다.

#### 감에 의존한 발주

- 과거 경험과 감각에 의존해 발주한다.
- 과잉재고 또는 결품이 빈번하게 발생한다.

#### 매출 분석의 부재

- 날씨, 요일, 시즌 등 외부 변수가 매출에 미치는 영향을 파악하지 못한다.
- POS, 재고, 발주 데이터가 분리되어 빠른 판단이 어렵다.

### 1.3 핵심 고객

| 고객 세그먼트 | 설명 |
|---|---|
| 음식점 및 카페 소상공인 | 식자재 회전율이 높고 일일 발주가 필요한 개인 매장 |
| 소규모 프랜차이즈 매장 | 본사 물류 외에 개별 식자재 관리가 필요한 가맹점 |
| 직접 관리하는 자영업자 | 전담 관리 직원 없이 점주가 직접 재고 관리와 발주를 수행하는 매장 |

개발 최우선 대상은 음식점 운영 소상공인이다.

### 1.4 가치 제안

"처음 한 번만 재고를 입력하세요. 이후의 재고 관리와 발주 판단은 AI가 모두 대신합니다."

### 2.3 UC-01 회원가입

#### 목적

점주가 사주라 서비스를 사용하기 위한 계정과 매장, 초기 운영 데이터를 등록한다.

#### 사전 조건

- 사용자는 Google, 카카오 또는 이메일/비밀번호 방식으로 가입할 수 있다.

#### 기본 흐름

1. 사용자가 Google, 카카오 또는 이메일/비밀번호 방식으로 회원가입을 시작한다.
2. 소셜 로그인인 경우 Frontend가 Backend의 OAuth 인가 URL로 이동한다.
3. Backend가 OAuth 콜백에서 사용자 정보를 조회한다.
4. 이메일/비밀번호 가입인 경우 Backend가 비밀번호를 해시하여 사용자 정보를 저장한다.
5. Backend가 회원 존재 여부를 확인하고 신규 사용자 정보를 저장한다.
6. Backend가 자체 JWT Access Token과 Refresh Token을 발급한다.
7. (사업자 검증 게이트 — 온보딩과 분리) 사용자가 사업자등록번호와 사업자등록증 파일을 입력한다.
8. Backend가 국세청 API로 계속사업자 여부를 검증하고, 통과 시 등록증 파일을 저장한 뒤 `business_status=PENDING`으로 둔다. 입력값이 마스터 코드면 호출 없이 곧바로 `VERIFIED`. `PENDING`·`VERIFIED`부터 온보딩 진입이 허용된다(승인 대기 중에도 진행 가능).
8a. (비동기) 관리자(`role=ADMIN`)가 `/admin` 심사 큐에서 등록증을 확인해 승인(`VERIFIED`) 또는 반려(`REJECTED`+사유)한다. 반려 시 사용자는 재검증한다.
9. 사용자가 매장명, 업종, 연락처, 주소, 매장 규모 구간, 운영 형태를 입력한다.
10. Backend가 매장 정보를 DB에 저장한다.
11. 사용자가 POS 연동 방식을 고른다. POS API(토스플레이스·키움페이·OKPOS)를 고르면 POS 종류와 자격증명을 입력하고 연동을 시도한다.
12. POS API 연동 성공 시 `pos_connections.status`를 `CONNECTED`로 설정한다.
13. POS API 미연동 또는 연동 실패 시 사용자가 CSV 모드를 선택하며, 이 경우 `pos_connections.status`를 `CSV_MODE`로 설정한다.
14. 사용자가 초기 재고를 입력한다.
15. Backend가 초기 재고를 DB에 저장한다.
16. 사용자가 초기 메뉴와 레시피를 입력한다.
17. Backend가 메뉴와 레시피를 DB에 저장한다.
18. Backend가 온보딩 완료 상태를 저장한다.
19. Frontend가 메인 화면을 제공한다.

#### 대안 흐름

- 사업자등록번호 검증 결과가 휴업·폐업·미등록·형식오류이거나 관리자가 반려(`REJECTED`)하면 계정을 삭제하지 않고 유지한 채 사업자 검증 화면에 머무르며, 미등록/형식은 재입력을, 휴업/폐업·반려는 사유를 안내한다. `UNVERIFIED`·`REJECTED` 상태에서는 온보딩으로 넘어가지 못한다(`PENDING`부터 허용).
- POS API 미연동·연동 실패 시 CSV 모드로 진행한다. CSV 모드에서도 수요예측·자동발주 추천 기능은 동일하게 동작한다 (`02_implementation_design.md` §1.3·§1.6 데모 시나리오 기준).
- 온보딩 도중 이탈한 사용자는 다음 로그인 시 `onboarding_completed: false` 상태로 기존 단계부터 재진입한다.

#### 사후 조건

- 점주, 매장 정보, 초기 재고, 초기 메뉴, POS 연동 상태, 온보딩 완료 여부가 저장된다.

### 2.4 UC-02 재고 관리

#### 목적

점주가 식자재 재고를 등록, 수정, 조회하고 폐기 처리한다.

#### 사전 조건

- 점주가 로그인되어 있다.
- 재고관리 또는 재고품목 정보가 존재하거나 등록 가능해야 한다.

#### 기본 흐름

1. 점주가 재고 관리 화면에 진입한다.
2. Frontend가 재고 목록을 요청한다.
3. Backend가 DB에서 재고를 조회한다.
4. Backend가 재고 목록을 Frontend에 반환한다.
5. Frontend가 재고 목록을 표시한다.

#### 등록 흐름

1. 점주가 재고 정보를 입력한다.
2. Frontend가 등록 요청을 보낸다.
3. Backend가 재고를 DB에 저장한다.
4. Frontend가 결과를 표시한다.

#### 수정 흐름

1. 점주가 재고 수정을 요청한다.
2. Backend가 기존 재고를 조회한다.
3. Backend가 재고 수정 내용을 DB에 반영한다.
4. Frontend가 결과를 표시한다.

#### 폐기 흐름

1. 점주가 폐기 요청을 입력한다.
2. Backend가 현재 재고 수량을 조회한다.
3. 폐기 가능 수량이 충분한 경우 Backend가 재고를 차감한다.
4. 수량 부족 또는 조건 불충분 시 Backend가 오류를 반환한다.

#### 사후 조건

- 재고품목의 현재수량이 최신 상태로 반영된다.

### 2.5 UC-03 판매 데이터 조회

#### 목적

점주가 기간별 판매 데이터를 조회한다.

#### 사전 조건

- 점주가 로그인되어 있다.
- POS 연동 또는 CSV 업로드를 통해 판매데이터가 저장되어 있다.

#### 기본 흐름

1. 점주가 판매 데이터 조회 화면에 진입한다.
2. 점주가 조회 기간을 선택한다.
3. Frontend가 판매 데이터 요청을 Backend에 보낸다.
4. Backend가 DB에서 기간별 판매 데이터를 조회한다.
5. Backend가 목록을 Frontend에 반환한다.
6. Frontend가 판매 목록을 표시한다.

#### 상세 조회 흐름

1. 점주가 판매 목록에서 특정 날짜를 선택한다.
2. Frontend가 그날의 판매 내역과 메뉴별 판매 수량을 요청한다.
3. Backend가 DB에서 그날의 판매 데이터를 조회한다.
4. Frontend가 시간대별 판매 내역, 메뉴별 판매 수량, 그날 총매출을 표시한다.

### 2.6 UC-04 메뉴 관리

#### 목적

점주가 판매 메뉴와 레시피를 관리한다.

#### 사전 조건

- 점주가 로그인되어 있다.

#### 기본 흐름

1. 점주가 메뉴 관리 화면에 진입한다.
2. Frontend가 메뉴 목록을 요청한다.
3. Backend가 DB에서 메뉴를 조회한다.
4. Frontend가 메뉴 목록을 표시한다.

#### 등록 흐름

1. 점주가 메뉴 정보를 입력한다.
2. Backend가 메뉴명 중복 여부를 확인한다.
3. 중복이 없으면 메뉴를 저장한다.
4. 레시피 입력이 있으면 레시피를 저장한다.
5. 중복이 있으면 오류를 반환한다.

#### 수정 흐름

1. 점주가 메뉴 수정을 요청한다.
2. Backend가 메뉴를 조회하고 수정 내용을 반영한다.
3. 레시피 수정이 있으면 레시피를 수정한다.

#### 삭제 흐름

1. 점주가 메뉴 삭제를 요청한다.
2. Backend가 메뉴의 소유권과 현재 삭제 여부를 확인한다.
3. Backend가 메뉴에 `is_deleted=true`, `deleted_at=현재시각`을 기록한다.
4. Backend가 운영 메뉴 목록에서 해당 메뉴를 제외한다.
5. 과거 판매 데이터는 기존 `menu_id` 참조를 유지한다.

### 2.7 UC-05 수요예측 관리

#### 목적

점주가 메뉴별 1-3일 예상 수요 및 추천발주량을 확인한다.

#### 사전 조건

- POS 판매 데이터가 존재한다.
- AI예측시스템이 예측 결과를 생성했거나 직접 호출 가능해야 한다.

#### 기본 흐름

1. 점주가 수요 예측 화면에 진입한다.
2. 점주가 기간을 설정한다.
3. Frontend가 예측 결과를 요청한다.
4. Backend가 DB에서 저장된 수요예측 결과를 조회한다.
5. 결과가 존재하면 Backend가 바로 반환한다.
6. 결과가 없으면 Backend는 수동 실행 가능 여부를 확인한다.
7. 수동 실행이 요청된 경우 Backend가 n8n 예측 워크플로우를 그 매장 하나로 실행시키고 저장된 결과를 반환한다.
8. 정기 배치 예측은 n8n이 DB/API 데이터를 수집, 전처리, 정규화하고 AI Server를 호출한 뒤 결과를 DB에 저장한다.
9. Frontend가 예측 결과와 예측 근거(`05_ai.md` §8)를 표시한다.

#### 예외 흐름

- POS 연동 실패 시 예측 불가.
- 신메뉴 출시 직후 또는 특수 행사 등 모델이 학습하지 못한 변수는 예측 신뢰도 낮음으로 표시한다.

### 2.8 UC-06 발주 요청

#### 목적

점주가 AI 추천발주안을 확인, 수정, 승인하고 쿠팡 장바구니 자동 담기를 수행한다.

#### 사전 조건

- 수요예측 결과(메뉴별 예상 수량)가 n8n 배치 워크플로우를 통해 DB에 사전 저장되어 있어야 한다.
- 점주가 로그인되어 있다.

#### 기본 흐름

1. 점주가 발주 요청 화면에 진입한다.
2. Frontend가 추천안을 요청한다.
3. Backend가 저장된 수요예측과 현재 재고로 추천발주를 계산한다(§3.7.2).
4. Frontend가 추천안을 표시한다.
5. 점주가 추천안을 확인한다.
6. 점주가 발주를 확정한다.
7. Backend가 발주 내역을 DB에 저장한다.
8. 사주라 확장이 쿠팡에서 품목을 검색하고 Backend가 담을 상품을 선택한다.
9. 사주라 확장이 점주 브라우저의 쿠팡 장바구니에 발주 목록을 추가한다.
10. Backend가 쿠팡 결제 진행 안내를 반환한다.
11. Frontend가 사용자에게 쿠팡에서 결제 진행 안내를 표시한다.

#### 대안 흐름

- 점주가 수량 또는 상품을 수정한다. 수정 중인 값은 서버에 저장하지 않고 확정 때 한 번에 보낸다.
- 점주가 추천을 거부하거나 수정한 경우 해당 패턴을 다음 추천에 반영한다.

#### 사후 조건

- 발주 내역이 저장된다.
- 장바구니 자동 담기 결과가 반환된다.
- 실제 결제는 쿠팡에서 진행된다.

## 3. 기능 명세

### 3.0 기능 분류

| 대분류 | 기능 | 정의 위치 |
|---|---|---|
| 인증/회원 | Google·카카오 로그인, 이메일 회원가입, 사업자 검증 게이트, 매장 정보 입력 | §3.1 |
| 메뉴 관리 | 메뉴 등록·조회·수정·삭제, 메뉴명 중복 검증, 레시피 관리 | §3.2 |
| 재고 관리 | 초기 재고 등록, 재고 조회·수정, 레시피 기반 자동 차감(FIFO), 폐기 처리, 소비기한 관리 | §3.3 |

### 3.1 인증 및 회원가입

- 사용자는 Google 또는 카카오 계정, 또는 이메일/비밀번호 방식으로 회원가입 및 로그인한다.
- 모든 인증 방식은 동일한 자체 JWT 구조를 사용한다.
- 회원가입 후 사용자는 사업자 검증과 온보딩에서 사업자등록번호, 매장 정보, POS 연동, 초기 재고, 초기 메뉴를 입력한다(§3.1.4).

#### 3.1.1 소셜 로그인 (Google / 카카오)

- Google과 카카오 모두 Authlib 라이브러리를 사용하여 Backend에서 OAuth 2.0 흐름을 처리한다. Firebase SDK 미사용.
- Frontend는 각 로그인 버튼 클릭 시 Backend의 인가 URL로 리다이렉트만 수행한다.
- Backend는 OAuth 콜백에서 사용자 정보를 조회하고, 회원 존재 여부를 DB에서 확인한다.
- 신규 사용자이면 회원 정보를 저장하고 온보딩 흐름을 시작한다.
- 인증 제공자와 무관하게 동일한 자체 JWT를 발급한다.
- Access Token은 콜백 응답 본문·URL에 노출하지 않는다. API: `02_implementation_design.md` §3.2 `GET /api/auth/callback/{provider}`.

로그인 흐름 (`{provider}` = `google` | `kakao`):

```
Frontend → GET /api/auth/login/{provider}
         → 302 Redirect → 제공자 OAuth 인가 페이지
         → 제공자 인증 완료
         → GET /api/auth/callback/{provider}?code=...
         → Backend: 제공자 사용자 정보 조회 → 자체 JWT 발급
         → Backend: Set-Cookie refresh_token + 302 Redirect → FE root("/")
         → Frontend 첫 진입: POST /api/auth/refresh (Cookie 자동 전송) → Access Token 수신 → 메모리 저장
         → Frontend: GET /api/auth/me → onboarding_completed 분기
```

| 구분 | 항목 |
|---|---|
| 입력 | OAuth 인가 코드 (Backend 콜백으로 수신) |
| 출력 | Set-Cookie refresh_token (HttpOnly) + 302 Redirect to FE root. Access Token은 FE 첫 진입 후 `POST /api/auth/refresh` 응답으로 수신, user_id·email·onboarding_completed는 `GET /api/auth/me`로 조회 |

#### 3.1.2 이메일/비밀번호 로그인

- 사업자가 직접 이메일과 비밀번호로 가입 및 로그인하는 방식.
- 비밀번호는 bcrypt로 해시하여 저장한다.
- 소셜 로그인 계정은 비밀번호 변경 기능을 사용할 수 없다.
- 이메일 회원가입(`POST /api/auth/register`)은 email·password·name만 받는다. 사업자등록번호·매장 정보는 가입 이후 사업자 검증·온보딩 단계(§3.1.4)에서 입력한다.

| 구분 | 항목 |
|---|---|
| 입력 | 회원가입: email, password, name / 로그인: email, password |
| 출력 | JWT Access Token, JWT Refresh Token, user_id, email, business_status, onboarding_completed |

#### 3.1.3 JWT 토큰 정책

모든 인증 방식(Google, 카카오, 이메일)에서 동일한 자체 JWT 구조를 사용한다. 유효 기간·저장 위치·Rotation은 `03_be.md` §7.3에서 정의한다.

#### 3.1.4 사업자 검증 및 온보딩 초기 설정

계정 생성 직후 매장 서비스 진입 전까지 아래 단계를 순서대로 진행한다. 각 단계는 직전 단계 완료 전에는 진입할 수 없다(가드).

```
1. 계정 생성 (Google / 카카오 OAuth 또는 이메일/비밀번호 회원가입) → business_status=UNVERIFIED
2. 사업자 검증 (온보딩과 분리된 독립 단계) — 사업자등록번호 입력 + 사업자등록증 업로드
     ├─ ① 국세청 API 즉시 검증 (존재·영업 여부)
     │      ├─ 미등록 / 형식 오류 → 재입력 요청 (상태 유지)
     │      └─ 휴업 / 폐업 → 진행 불가, 사유 안내 (상태 유지)
     └─ ② 계속사업자 통과 시 사업자등록증 업로드 → business_status=PENDING (관리자 심사 대기)
            · PENDING부터 온보딩 진행 허용 (관리자 승인을 기다리지 않음)
            · 관리자 승인 → VERIFIED / 반려 → REJECTED(사유) → 재검증
3. 매장 정보 입력 (매장명, 업종, 연락처, 주소, 매장 규모 구간, 운영 형태)
4. POS 연동 방식 선택
     ├─ CSV 모드 (pos_connections.status=CSV_MODE)
     └─ POS API 연동 → POS 종류·자격증명 입력 → 연동 시도
                              ├─ 성공: pos_connections.status=CONNECTED
                              └─ 실패: CSV 모드로 진행 (status=CSV_MODE)
     · 양쪽 모두 수요예측·자동발주 추천 활성화
     · 설정 화면에서 모드 전환 가능
5. 초기 재고 / 초기 메뉴 입력
6. 메인 화면 진입 (onboarding_completed=true)
```

사업자 검증은 국세청 API 자동 검증과 관리자 승인을 병행한다. 사업자의 실재·영업 여부는 국세청 API로, 소유권은 사업자등록증 업로드와 관리자 심사로 확인한다.

- 상태 모델 `business_status`: `UNVERIFIED` → (국세청 API 통과 + 등록증 업로드) `PENDING` → (관리자 승인) `VERIFIED` / (반려) `REJECTED`.
- 온보딩 진입 가드: `PENDING` 또는 `VERIFIED`면 온보딩 진입 허용. `UNVERIFIED`·`REJECTED`면 검증 화면으로 강제 이동. 등록증을 올려 `PENDING`이 되면 관리자 승인 전이라도 온보딩·서비스 사용이 가능하고, 관리자는 사후 반려로 차단할 수 있다.
- 검증 실패 시 계정을 삭제하지 않고 유지한다. 미등록/형식은 재입력, 휴업/폐업·반려는 사유를 표시하고 재검증을 안내한다.
- 재접속 시 `GET /api/auth/me`의 `business_status`·`onboarding_completed`로 Frontend가 검증/온보딩 화면으로 강제 이동한다.
- 소셜·이메일 계정 모두 동일하게 사업자 검증 단계를 거친다(인증 방식 무관).
- 관리자 심사: 관리자(`users.role=ADMIN`)가 `/admin` 심사 큐에서 `PENDING` 목록·업로드 등록증을 보고 승인/반려한다.
- 시연·테스트용 강제 패스: 입력 사업자번호가 환경변수 마스터 코드(`NTS_MASTER_BYPASS_CODE`)와 일치하면 국세청 호출·등록증 업로드 없이 곧바로 `VERIFIED` 처리한다. 운영 조건은 `03_be.md` §7.4.
- POS 연동 상태(`pos_connections.status` — `CONNECTED` / `ERROR` / `CSV_MODE` / `DISCONNECTED`, `02_implementation_design.md` §4.3.4)는 온보딩 완료 후 `GET /api/store/pos/status`로 별도 조회한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 사업자등록번호 + 사업자등록증 파일 | 필수, 국세청 API 검증 + 업로드. `POST /api/store/business/verify` (multipart) |
| | 매장명 | 필수 |
| | 업종 | 필수 |
| | 연락처 | 필수 |
| | 주소 | 필수 (AI 예측 지역 변수 활용) |
| | 매장 규모 구간 | 필수, 선택지 제공 (소형 ~10석 / 중형 11~30석 / 대형 31석~) |
| | 운영 형태 | 필수, 선택지 제공 (홀 운영 / 배달 전용 / 홀+배달 병행) |
| | POS 종류 및 자격증명 | POS API 선택 시 필수. 종류는 토스플레이스 / 키움페이 / OKPOS |
| 출력 | store_id | |
| | business_status | UNVERIFIED / PENDING / VERIFIED / REJECTED |
| | onboarding_completed | boolean |

### 3.2 메뉴 관리

- 메뉴는 재고와 직접 연결되지 않고 레시피를 통해 재료항목과 연결된다.
- 레시피는 메뉴별 재료 사용량을 관리한다. 레시피 재료는 같은 매장의 재고 목록에 등록된 재료만 쓴다.
- 재고 차감 ON인 메뉴는 항상 재료 1개 이상의 레시피를 가진다. 레시피가 없으면 재고 차감을 켤 수 없고, 재고 차감 ON 상태에서는 레시피를 비우거나 삭제할 수 없다(`MENU_RECIPE_REQUIRED`).

#### 3.2.1 메뉴 조회

- 점주가 등록한 메뉴 목록을 조회한다.

| 구분 | 항목 |
|---|---|
| 입력 | store_id |
| 출력 | 메뉴 목록 (menu_id, 메뉴명, 가격, 재고차감_사용 여부, 레시피 존재 여부) |

#### 3.2.2 메뉴 등록

- Backend Service 계층에서 메뉴명 중복을 검증한다.
- 중복이 없으면 메뉴를 저장한다.
- 메뉴는 재고 차감 OFF로 등록된다. 레시피를 저장한 뒤 재고 차감을 켠다(§3.2).

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 메뉴명 | 필수, 중복 불가 |
| | 가격 | 필수 |
| 출력 | menu_id | |
| | 저장 완료 여부 | |

#### 3.2.3 메뉴 수정

- 기존 메뉴를 조회한다.
- 수정 요청 내용을 반영한다.
- 레시피 수정이 있으면 레시피도 수정한다.

| 구분 | 항목 |
|---|---|
| 입력 | menu_id, 수정할 항목 (메뉴명 / 가격 / 재고 차감 사용 여부 / 레시피) |
| 출력 | 수정 완료 여부 |

#### 3.2.4 메뉴 삭제

- 점주 UI에서는 즉시 삭제로 표시되나 DB에는 소프트 삭제로 처리한다.
- 삭제된 메뉴는 운영 메뉴 목록에서 제외하되 DB에는 유지한다.
- 삭제된 메뉴의 과거 판매 데이터는 `menu_id` 참조로 계속 유지한다.
- 메뉴명 중복 검증은 동일 매장의 삭제되지 않은 메뉴만 대상으로 수행한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | menu_id | |
| 출력 | 삭제 완료 여부 | |
| DB 처리 | is_deleted: true, deleted_at 기록 | 소프트 삭제 |

### 3.3 재고 관리

#### 3.3.1 초기 재고 등록

- 사용자가 초기 재고를 1회 입력한다.
- 재고관리와 재고품목으로 저장한다.
- 단위는 선택지로 제공한다 (kg / g / L / ml / 개).
- 등록 수량이 0보다 크면 첫 로트로 저장한다 (입고일 = 등록일).
- 단가는 재료 단위당 금액(원)이다. 점주가 입력하거나 수정하지 않는다.
- 단가 출처는 매장 공용 쿠팡 상품 테이블 하나다. 테이블은 상품 고유 ID(`productId` + `vendorItemId`)·상품명·판매가·상품 1개 용량·최종 갱신 시각을 담고, 매장 정보는 담지 않는다.
- 판매가는 조건 없이 누구나 받는 가격으로, 검색 결과·상품 페이지의 표시 가격이다. 회원 조건 할인은 넣지 않는다. 할인 표시가 '와우할인'·'와우쿠폰할인'처럼 와우 회원 할인인 상품은 판매가를 갱신하지 않는다. 처음 저장하는 상품이면 판매가를 비운다.
- 상품 1개 용량은 쿠팡 단위가격 표시(예: '100g당 2,348원')에서 구한다. 단위가격 표시는 표시 가격 기준이므로 `표시 가격 ÷ 단위가격 × 기준 수량`이 용량이다(예: 11,740 ÷ 2,348 × 100g = 500g, 9,460 ÷ 946 × 1구 = 10구). 단위가격 표시가 없으면 용량은 비운다.
- 공용 쿠팡 상품은 쿠팡 자동 담기 중 서버가 받은 쿠팡 화면(요소 목록)의 상품 카드 값으로 저장·갱신한다. 담지 않은 상품도 화면에 나온 상품이면 모두 저장·갱신한다. 같은 상품(`productId` + `vendorItemId`)은 한 행으로 갱신하고 새 행을 만들지 않는다(`04_fe.md` §12.5). 쿠팡 Open API는 판매자 자기 상품 관리용이라 가격 출처가 아니고, 서버 크롤링은 하지 않는다.
- 계산한 상품 1개 용량이 상품명의 용량 표기(예: '500g, 4개' → 2kg)와 2% 넘게 다르면 잘못 읽은 값으로 보고 그 상품의 공용 값을 갱신하지 않는다. 처음 저장하는 상품이면 판매가·용량을 비운다. 상품명에 용량 표기가 없거나 용량 단위 계열(무게·부피·개수)이 다르면 대조하지 않는다.
- 이미 저장된 공용 쿠팡 상품과 판매가가 20% 이상 다른 값(`|보낸 판매가 − 저장된 판매가| ÷ 저장된 판매가 ≥ 0.2`)은 공용 쿠팡 상품에 바로 반영하지 않고 가격 후보로 보관한다. 담기 결과 기록과 재고 품목의 연결은 정상 처리한다.
- 가격 후보는 상품·보낸 매장·판매가·받은 시각이다. 같은 매장이 같은 상품의 후보를 다시 보내면 덮어쓰고, 받은 지 14일이 지난 후보는 버린다.
- 다른 매장이 보낸 판매가가 어떤 후보와 20% 이내이면 그 값으로 공용 쿠팡 상품을 갱신하고 그 상품의 후보를 모두 지운다. 같은 매장이 반복해 보낸 값은 확인으로 치지 않는다.
- 매장 재고 품목은 공용 쿠팡 상품 하나를 가리킨다. 자동 담기에 성공하면 그 상품으로 연결하고, 다른 상품을 담으면 연결을 덮어쓴다(§3.8.1).
- 단가는 연결된 공용 쿠팡 상품으로만 계산한다.
  1. 상품 1개 용량이 재료 단위로 환산되면 `판매가 ÷ 용량(재료 단위)`을 쓴다. 무게(g·kg)는 무게끼리, 부피(ml·L)는 부피끼리, 개수 단위(개·구·입 등)는 재료 단위 '개'로 환산한다.
  2. 환산되지 않으면 `판매가 ÷ 포장 수량`을 쓴다. 포장 수량은 상품 1개에 든 재료 수량(재료 단위)이다. 자동 담기의 LLM이 상품명에서 판정하고, LLM이 판정하지 못하면 점주가 입력한다.
  3. 연결이 없거나, 판매가가 비었거나, 1·2로 계산할 수 없으면 단가는 미설정이다.
- 포장 수량은 매장 재고 품목에만 저장한다. 점주 입력은 공용 쿠팡 상품에 쓰지 않는다.
- 구매 금액은 로트 하나의 실제 지출(원)이다. 단가를 바꾸지 않는다.
- 시장 시세 참고는 KAMIS(한국농수산식품유통공사) 농산물유통정보 오픈API의 주요 식자재 일별 소매가로 한다 — 홈 화면 노출(`04_fe.md` §4.3), 계약은 `02_implementation_design.md` §3.5. KAMIS 값은 단가로 쓰지 않는다.

|---|---|---|
| 입력 | 재료명 | 필수 |
| | 현재 수량 | 필수 |
| | 단위 | 필수, 선택지 제공 (kg / g / L / ml / 개) |
| | 소비기한 | 선택 |
| | 구매 금액 | 수량이 0보다 크면 필수. 등록 수량 전체의 금액(원) |

| 상세 출력 | 로트 목록 (lot_id, 입고 수량, 현재 수량, 소비기한, 입고일, 구매 금액) |

#### 3.3.3 자동 재고 차감 (FIFO)

- POS 판매 데이터가 저장된다.
- 판매 메뉴를 레시피와 매핑한다. 재고 차감이 꺼진 메뉴(`use_inventory_deduction=false`)와 레시피가 없는 메뉴는 차감하지 않는다.
- 레시피 사용량은 재료의 재고 단위로 본다. 단위 환산은 없다.
- 재료마다 '차감 기준 시각'보다 뒤에 팔린 판매만 차감한다. 차감 기준 시각은 품목 등록 시각에서 시작하고, 차감할 때마다 차감한 판매 중 가장 늦은 판매 시각으로 옮긴다. 기준 시각보다 앞선 판매는 저장만 하고 차감하지 않는다.
- 이미 저장된 판매와 중복되어 건너뛴 행은 차감하지 않는다.
- 소비기한이 가장 빠른 로트부터 순서대로 차감한다 (FIFO). 소비기한이 없는 로트는 소비기한이 있는 로트 뒤에 입고일 순으로 차감한다.
- 한 로트의 수량이 부족하면 다음 로트로 이어서 차감한다.
- 모든 로트를 합산해도 수량이 부족하면 0에서 멈추고 '재고 확인 필요' 상태로 표시한다. 기록상 재고 없이 판매가 일어난 것으로, 입고 등록 누락이나 실사 오차를 뜻한다.
- '재고 확인 필요'는 해당 품목에 입고를 등록하거나 실사 조정(사유 `STOCKTAKE`)으로 로트를 수정하면 해제한다.
- 재고 부족 발생 시 점주에게 알림을 발송하고 홈/대시보드에 경고 배지를 노출한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 판매된 메뉴 목록 + 수량 (POS 데이터) | |
| 출력 | 차감에 반영된 판매 건수 | |
| | 재고 확인 필요 재료 목록 | 이번 차감으로 새로 '재고 확인 필요'가 된 재료, 알림 트리거 |

#### 3.3.4 재고 수동 수정

- 신규 입고 시 기존 로트를 수정하지 않고 새 로트를 추가한다 (수량 + 소비기한 + 구매 금액 입력).
- 기존 로트의 소비기한 또는 수량을 직접 수정할 수 있다.
- 수정 이력을 기록한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 (신규 입고) | item_id, 입고 수량, 입고일, 소비기한, 구매 금액 | 새 로트 생성. 소비기한 선택, 구매 금액은 입고 수량 전체의 금액(원) |
| 입력 (기존 로트 수정) | lot_id, 수정 수량 또는 소비기한 | |
| 입력 공통 | 수정 사유 | 필수, 선택지 제공 (실사 조정 / 소비기한 정정 / 기타) |
| 출력 | 수정 완료 여부 | |
| 이력 기록 | 수정 전 수량, 수정 후 수량, 수정 전/후 소비기한, 수정 사유, 수정 일시, user_id | |

#### 3.3.5 재고 폐기

- 점주가 폐기할 로트를 골라 폐기 수량을 입력한다. 소비기한 초과 폐기 요청 알림(§3.3.6)에서 이동하면 해당 로트가 선택된 상태다.
- 서버는 해당 로트의 잔여 수량을 조회한다.
- 잔여 수량이 충분하면 그 로트에서 차감한다.
- 잔여 수량보다 많으면 오류를 반환한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | item_id, lot_id, 폐기 수량, 폐기 사유 | 폐기 사유 선택 |
| 출력 | 폐기 완료 여부 | |
| | 차감 후 로트 잔여 수량 | |
| 오류 | 로트 잔여 수량 부족 시 오류 반환 | |

#### 3.3.6 소비기한 관리

- 매일 01:30 BE가 ARQ `cron_jobs`로 전체 로트의 소비기한을 체크한다. AI 야간 배치(n8n 02:00, §3.11.1)와 시각을 분리한다.
- 점주가 직접 소비기한 초과 재료를 폐기 처리한다.

| 조건 | 처리 |
|---|---|
| 소비기한 D-3일 (`expiry_date` = 오늘 + 3일) | 경고 알림 발송 + 재고 목록에 경고 표시 |
| 소비기한 D-1일 (`expiry_date` = 오늘 + 1일) | 긴급 알림 발송 + 재고 목록에 긴급 표시 |
| 소비기한 초과 첫날 (`expiry_date` = 어제) | 점주에게 폐기 요청 알림 발송 (자동 폐기 없음) |

- '오늘'은 배치 실행일(한국 시각)이다. 남은 수량이 0보다 큰 로트만 대상이다.
- 알림은 품목·조건마다 한 건이고, 본문에 해당 로트 수를 담는다.
- 같은 날 같은 품목·조건 알림이 이미 있으면 다시 만들지 않는다.

실행 흐름

| 단계 | 작업 | 실패 처리 |
|---|---|---|
| 1. cron 트리거 | ARQ `cron_jobs`가 매일 01:30에 `InventoryService.check_expiry_batch` 호출 | ARQ 재시도 정책 |
| 2. 로트 조회 | `InventoryService.check_expiry_batch`가 `inventory_lots`에서 `expiry_date` 기준 D-3·D-1·초과 매칭 로트 조회 | sentry-sdk 자동 포착 |
| 3. 알림 발송 | `NotificationService.create_and_push` 호출 → `notifications` INSERT + `push_subscriptions` 대상 Web Push (pywebpush) | NotificationService 내부 처리 |

| 구분 | 항목 |
|---|---|
| 입력 | 전체 로트의 소비기한 |
| 출력 | 소비기한 임박/초과 로트 목록, 알림 발송 여부 |

### 3.4 POS 연동

- POS별 데이터 형식 차이를 처리하기 위해 공통 중간 스키마와 어댑터 패턴을 적용한다.

#### 3.4.1 지원 방식

- CSV 업로드
- POS API 연동 (토스플레이스·키움페이·OKPOS)

#### 3.4.2 어댑터 구조

| POS 소스 | 어댑터 | 공통 스키마 |
|---|---|---|
| CSV 업로드 | CSVAdapter | `{ "sold_at": ..., "external_sale_id": ..., "menu_name": ..., "quantity": ..., "unit_price": ..., "total_price": ... }` |
| 토스플레이스 | TossPlaceAdapter | 동일 공통 스키마 |
| 키움페이 | KiwoomAdapter | 동일 공통 스키마 |
| OKPOS | OKPOSAdapter | 동일 공통 스키마 |

- POS 어댑터의 공통 스키마는 판매 메뉴 단위의 표준 판매 데이터이다.
- Backend는 공통 스키마의 `menu_name`을 매장 메뉴와 매핑하여 내부 `menu_id`를 결정한다.
- `external_sale_id`는 POS/CSV 원본 판매 식별자이며, 제공되지 않는 CSV 데이터에서는 NULL을 허용한다.
- 매핑 실패 시 해당 행은 저장하지 않고 업로드/동기화 결과의 `skipped` 항목으로 반환한다.

#### 3.4.3 POS API 연동

- 지원 POS사는 토스플레이스·키움페이·OKPOS 세 곳으로 한정한다. 저장 코드값은 `TOSSPLACE` / `KIWOOM` / `OKPOS`다.
- 회사별 인증 방식·자격증명 필드·수집 방식(웹훅/주기 조회)은 조사 후 확정한다 (`docs/research/backend/13_pos_adapter.md`).

#### 3.4.4 CSV 업로드

- 사주라가 제공하는 고정 템플릿 형식만 허용한다.
- 템플릿 다운로드는 POS 연동 설정 화면에서 제공한다. 업로드 화면은 실제 파일 업로드만 담당한다. 온보딩의 POS 연동 단계는 모드 선택만 수행한다.
- 지원 포맷: CSV(UTF-8) 단일. Excel(.xlsx) 미지원.
- 업로드 시 컬럼명을 동적으로 매핑한다(`date_column`·`menu_column`·`quantity_column`·`price_column`, 선택: `external_sale_id_column`).
- 메뉴 자동 등록 옵션(`auto_create_menus=true`): CSV에 있는 미등록 메뉴명을 매장 메뉴에 즉시 추가한다. 카테고리는 `"자동등록"`, 단가는 `total_price / quantity`, `use_inventory_deduction=false`. 점주가 메뉴 화면에서 사후 수정 가능. 기본값은 `false`(미등록 행은 skip).
- 결과의 그룹화 사유: `02_implementation_design.md` §3.6 API 응답 정의.

### 3.6 수요예측

- 시스템은 과거 매출과 외부 변수(날씨·캘린더·지역 — `05_ai.md` §4)를 반영해 매장 일 매출을 1~3일 예측한다.

- 예측 대상은 재고 차감 여부와 무관하게 전체 메뉴이다.
- 예측 결과는 DB에 사전 저장하여 점주 요청 시 즉시 반환한다.

| 구분 | 항목 |

#### 3.6.2 예측 결과 조회 (점주 요청)

- DB 캐시를 우선 조회하여 반환한다.
- 저장된 예측 결과가 없으면 점주가 수동 실행을 요청할 수 있다. Backend는 n8n 예측 워크플로우(§3.11.1)를 그 매장 하나로 실행시키고, 끝나면 저장된 결과를 반환한다.

| 입력 | store_id, menu_id (선택) | |
| 출력 | 메뉴별 1~3일 예상 수요 | |
| | 예측 근거 | `05_ai.md` §8 |
| | 신뢰도 낮음 경고 배지 | §3.6.3 조건 중 하나라도 해당 시 표시 |

#### 3.6.3 신뢰도 경고 기준

- 예측 결과가 아래 트리거 중 하나라도 해당하면 "신뢰도 낮음" 경고 배지를 표시한다.
- `low_confidence_reason`은 우선순위(표의 위→아래)가 가장 높은 트리거의 코드다.

| 우선순위 | reason 코드 | 조건 |
|---|---|---|
| 1 | `SHORT_HISTORY` | 매장 학습 영업일 < 60일 |
| 2 | `MISSING_FEATURES` | core lag 피처(직전 매출·7일 평균·같은 요일) 결측 |
| 3 | `SPECIAL_DAY` | 공휴일(대체공휴일 포함) |
| 4 | `LONG_HORIZON` | 선행 D+3 이상 |
| 5 | `WIDE_INTERVAL` | 상대 예측 구간 폭 (P90−P10)/기준선 > θ — θ는 재학습 시 train 구간 in-sample 폭의 P80로 재산정 |
| 6 | `DRIFT` (운영) | 직전 4주 rolling에서 모델 MAE > MA-7 MAE — 해당 기간 전 예측에 배지(`05_ai.md` §10) |

- 판정 결과는 `forecast_results.is_low_confidence` / `low_confidence_reason` 컬럼에 저장한다(`02_implementation_design.md` §4.3.14).
- 예측 근거 문구(`05_ai.md` §8)는 본 배지·P10/P90 구간과 항상 동반 노출한다.

### 3.7 추천발주

#### 3.7.1 추천발주 생성

- 점주가 추천발주를 요청할 때 Backend가 저장된 수요예측(§3.6.1)으로 계산한다. 배치로 미리 만들지 않는다.
- 발주 연동 대상은 쿠팡이다.
- 리드타임과 안전재고는 점주가 재료별로 직접 입력한다.
- 리드타임과 안전재고는 `inventory_items.lead_time_days`, `inventory_items.safety_stock`에 재료별로 저장한다.
- 리드타임 또는 안전재고가 미설정이면 시스템 기본값(리드타임 1일, 안전재고 0)으로 계산하되, 해당 품목에 `DEFAULT_USED` 상태를 표시하고 설정 필요 항목으로 안내한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 수요예측 결과 | 메뉴별 일일 예상 판매량 |
| | 레시피 소모량 | 메뉴→재료 변환 |
| | 현재 재고 | DB 실시간 조회 |
| | 입고 예정량 | 확정 후 도착 전인 발주 수량 |
| | 리드타임 | 점주 직접 입력 (일 단위) |
| | 안전재고 | 점주 직접 입력 (재료 단위) |
| 출력 | 품목별 권장 발주 수량 | |
| | 예상 소진 시점 | |
| | 추천 근거 | |

#### 3.7.2 추천발주 산식

추천발주는 점주가 요청할 때 Backend가 계산한다. 입력은 저장된 메뉴별 예상 수량(§3.6), 레시피, 그 시점의 현재 재고·입고 예정량, 리드타임, 안전재고다. 저장된 예측이 없으면 계산하지 않는다(§3.6.2).

레시피 사용량은 재고 단위로 보고 환산하지 않는다(§3.3.3).

```
대상 기간 = 예측 대상 일수 (target_dates 개수)
메뉴별 대상 기간 예상 판매량 = 대상일별 저장된 메뉴 예상 수량의 합
일일 소모량 = Σ (메뉴별 대상 기간 예상 판매량 × 레시피 재료 사용량) ÷ 대상 기간
입고 예정량 = Σ 입고 대기 상태인 발주 품목의 확정 수량 (§3.7.5)
발주 필요량 = 일일 소모량 × (대상 기간 + 리드타임) + 안전재고 − 현재 재고 − 입고 예정량
권장 발주 수량 = max(발주 필요량, 0)  ← 음수이면 발주 불필요
예상 소진 시점 = 판매 이력 마지막 영업일 + ⌈현재 재고 / 일일 소모량⌉일 (일일 소모량 0이면 없음)
```

- 예상 소진 시점은 입고 예정량을 넣지 않는다. 도착 전 재고는 소진을 늦추지 않는다.

산식 예시 (원두)

| 항목 | 값 |
|---|---|
| 대상 기간 | 3일 |
| 일일 원두 소모량 | 750 g (아메리카노 50잔 × 15 g) |
| 리드타임 | 2일 |
| 안전재고 | 1,000 g |
| 현재 재고 | 2,000 g |
| 발주 필요량 | 750 × (3 + 2) + 1,000 − 2,000 = 2,750 g |
| 예상 소진 시점 | 마지막 영업일 + ⌈2,000 / 750⌉ = 3일 후 |

#### 3.7.3 추천발주 조회 (점주 요청)

| 구분 | 항목 |
|---|---|
| 입력 | store_id |
| 출력 | 품목별 권장 발주 수량, 예상 소진 시점, 추천 근거 |

#### 3.7.4 점주 수정 및 승인

- 점주가 추천발주안을 확인한다.
- 점주가 수량 또는 품목을 수정할 수 있다.
- 점주가 발주를 확정한다.
- 점주 수정 이력과 실제 판매 결과는 모델 재학습 피드백으로 반영한다.

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 수정된 발주 수량 또는 품목, 승인 여부 | |
| 출력 | 승인된 발주 내역 | |
| 이력 기록 | 추천 수량, 확정 수량, 확정 일시 | 모델 재학습 피드백 활용 |

- 확정 시 품목마다 그 시점의 단가(§3.3.1)를 저장한다. 단가가 미설정이면 단가와 소계를 비운다.

#### 3.7.5 입고 처리

- 확정된 발주의 품목마다 입고 상태를 둔다. 확정 시 '입고 대기'이고, 처리하면 '입고 완료' 또는 '입고 안 함'이 된다.
- 입고 처리: 점주가 입고 수량·입고일·소비기한(선택)·구매 금액을 입력하면 그 값으로 로트를 만들고 '입고 완료'로 바꾼다.
- 입력 기본값은 입고 수량 = 확정 수량, 입고일 = 오늘, 소비기한 = 빈칸, 구매 금액 = 확정 시 소계(비어 있으면 빈칸)다. 점주는 모두 고칠 수 있다.
- 입고 안 함: 끝내 오지 않은 품목을 로트 없이 닫는다.
- 품목 하나는 한 번만 처리한다. 확정 수량과 다른 양이 오면 받은 양을 입고 수량으로 넣고, 남은 양은 따로 추적하지 않는다.
- 재고 화면에서 재료를 펼치면 그 재료의 '입고 대기' 품목을 확정일이 오래된 순으로 맨 위에 보여준다.

### 3.8 쿠팡 장바구니 자동 담기

- 점주가 발주를 확정하면 발주 기록을 저장한다.
- 점주가 자동 담기를 요청하면 사주라 브라우저 확장이 점주 브라우저에서 쿠팡 장바구니에 발주 목록을 담는다.
- 서버는 담을 상품을 고르는 판단만 수행하고 쿠팡 자격증명을 보유하지 않는다.
- Backend가 담기 결과를 기록하고 발주 상태를 갱신한다.
- Frontend는 쿠팡에서 결제 진행 안내를 표시한다.
- 확장 구조·권한·데이터 범위·LLM 사용 경계: `04_fe.md` §12.

#### 3.8.1 장바구니 자동 담기

| 구분 | 항목 | 비고 |
|---|---|---|
| 입력 | 승인된 발주 내역 (품목명, 수량) | 점주 승인 후 트리거. 확장 미설치 시 담기 버튼 비활성 |
| 출력 | 장바구니 담기 성공/실패 여부 | |
| | 담기 완료 품목 목록 | |
| | 실패 품목 목록 | 실패 시 반환 |

- 검색이 필요한 품목은 재료명을 그대로 검색어로 쿠팡을 검색한다. LLM은 검색 결과에서 상품 1개를 고르고 포장 수량을 판정한다. 담을 개수는 LLM이 아니라 서버가 계산한다. LLM은 담기 요청 1회에 한 번 부르고, 검색이 필요한 품목이 없으면 부르지 않는다. 입력·답 검사, 호출 횟수 제한, 시연용 보안 분류기: `03_be.md` §2.4.
- LLM은 아래 순서로 상품을 고른다.
  1. 재료와 같은 식자재만 후보로 둔다. 양념·조리 상품, 다른 부위·다른 품목, 재료가 일부만 든 세트는 뺀다. 비로그인이면 로켓프레시 상품도 뺀다.
     - 손질 형태가 다르면 다른 식자재다. 상품명에 재료명에 없는 손질 형태 표시가 있으면 뺀다. 손질 형태 표시는 원물을 자르거나 다듬은 상태를 나타내는 말이다(예: 대패·큐브·한입·슬라이스·채·다진·깐·손질·절단·칼집, '5mm'·'3~5cm' 같은 절단 크기).
     - 재료명에 손질 형태가 있으면(예: '대패삼겹살'·'깐양파') 그 형태 표시가 있는 상품만 둔다.
     - '구이용'·'찌개용' 같은 용도 표시는 손질 형태 표시가 아니다.
     - 냉동 여부가 다르면 다른 식자재다. 재료명에 '냉동'이 없으면 냉동 상품을 빼고, 있으면 냉동 상품만 둔다.
  2. 후보마다 재료 단위당 가격(표시 가격 ÷ 상품 1개 용량)을 구한다. 표시 가격은 검색 결과 카드의 최종 가격이고, 로그인 상태의 와우 가격도 그대로 쓴다.
  3. 재료 단위당 가격이 가장 낮은 후보보다 10% 이내로 비싼 후보만 남긴다.
  4. 남은 후보 중 별점이 가장 높은 상품을, 별점이 같으면 리뷰 수가 많은 상품을, 리뷰 수도 같으면 재료 단위당 가격이 낮은 상품을 고른다. 별점·리뷰 수가 없는 상품은 가장 낮은 값으로 본다.
- 검색이 필요한 품목은 연결된 쿠팡 상품이 없거나, 연결 시각부터 3일이 지났거나, 포장 수량을 알 수 없는 품목이다. 나머지 품목은 검색과 LLM 선택 없이 연결된 상품을 담는다.
- 연결 상품의 포장 수량은 상품 1개 용량이 재료 단위로 환산되면 그 용량, 아니면 재고 품목에 저장된 포장 수량이다(§3.3.1). 검색으로 고른 상품의 포장 수량은 상품 1개 용량이 재료 단위로 환산되면 그 용량, 아니면 LLM 판정값이고, 둘 다 없으면 그 품목은 실패다. 담을 개수는 `발주 수량 ÷ 포장 수량`을 올림한 값이다.
- 담기에 성공한 품목은 재고 품목의 연결을 담은 상품으로 바꾼다. 검색으로 고른 상품이면 연결 시각을 담기 시각으로 갱신하고, 연결 상품을 담았으면 연결 시각을 그대로 둔다.
- 연결 상품이 바뀌면 재고 품목의 포장 수량을 LLM 판정값으로 바꾸고, 판정값이 없으면 비운다.
- 확장이 쿠팡에 로그인되어 있지 않으면 로켓프레시 상품은 담을 수 없다. 이때 LLM은 로켓프레시 상품을 고르지 않고, 연결 상품이 로켓프레시인 품목은 검색이 필요한 품목으로 본다(`04_fe.md` §12.6).

### 3.11 데이터 파이프라인

#### 3.11.1 야간 배치 파이프라인

- 예측 배치는 매일 02:00(한국 시각)에 전체 매장으로 실행한다. 점주 수동 실행(§3.6.2)은 같은 워크플로우를 매장 하나로 실행한다.
- 책임 분리 — n8n은 모델 예측(입력 조회·외부 데이터 수집·전처리, AI Server 예측 호출, 예측 결과 저장, 실행 이력 기록)만 맡는다. 추천발주는 만들지 않는다. 추천발주 산식은 Backend가 점주 요청 시 계산한다(§3.7.2).
- AI Server는 n8n이 보낸 이력으로 매장 일 매출과 대상일별 메뉴 예상 수량을 예측한다.
- Backend는 예측 조회, 수동 실행 요청, 예측 완료 알림을 맡는다.
- 매장 하나의 실패는 다른 매장 처리를 멈추지 않는다.
- 판매 이력이 부족한 매장(AI Server 422)은 재시도·Slack 없이 실패로 기록한다. 그 밖의 실패는 3회 자동 재시도 후에도 지속되면 Slack 알림을 발송한다.
- 날씨는 매장 위치 기준이다. 판매 이력 기간과 어제까지의 대상일은 기상청 ASOS 일자료(매장에서 가장 가까운 관측소), 오늘 이후 대상일은 기상청 단기예보(매장 예보 격자)를 쓴다. 날짜마다 최저기온·최고기온·강수량을 보낸다.
- 매장 위치는 Backend가 점주가 주소를 저장할 때 주소를 좌표로 바꿔 정한다(예보 격자·가장 가까운 ASOS 관측소). 좌표 변환에 실패해도 주소 저장은 성공하고 위치는 비운다. 위치가 없는 매장은 날씨 없이 예측한다.
- 관측 날씨는 관측소·날짜 단위로 DB에 쌓는다(`02_implementation_design.md` §4.3.25). 배치는 그 관측소에 없는 날짜만 기상청에서 받는다. 예보는 매번 새로 받고 저장하지 않는다.
- 날씨 수집 실패는 예측을 막지 않는다. 받지 못한 날짜는 날씨 없이 보낸다.

| 단계 | 작업 | 실패 처리 |
|---|---|---|
| 1. 작업 시작 기록 | n8n이 매장별로 `pipeline_jobs`에 `store_id`, `type=FORECAST`, `triggered_by`(야간 `N8N`·수동 `USER`), `status=RUNNING`으로 INSERT | 3회 재시도 → Slack 알림 |
| 2. DB 데이터 조회 | n8n이 매장의 일별 매출·건수와 메뉴별 일 판매 수량을 조회 | 3회 재시도 → Slack 알림 |
| 3. 외부 데이터 수집 | n8n이 매장 위치로 기상청을 호출 — 관측 날씨는 DB에 없는 날짜만 ASOS 일자료로 받아 저장, 대상일은 단기예보 (`05_ai.md` §4.2) | 3회 재시도 후 날씨 없이 진행 |
| 4. 입력 데이터 전처리/정규화 | n8n Code Node에서 날짜 정렬, 외부 변수 병합 후 AI Server 입력 스키마로 변환 | 3회 재시도 → Slack 알림 |
| 5. 수요예측 실행 | n8n이 AI Server `/ai/forecast/predict`를 호출 — 매장 일 매출과 대상일별 메뉴 예상 수량 | 3회 재시도 → Slack 알림 |
| 6. 예측 결과 저장 | n8n이 `forecast_results`·`forecast_menu_items`에 UPSERT. 같은 매장·대상일 결과는 덮어쓴다 (`02_implementation_design.md` §4.3.14·§4.3.15) | 3회 재시도 → Slack 알림 |
| 7. 작업 종료/알림 | n8n이 `pipeline_jobs`를 `DONE` 또는 `FAILED`로 UPDATE. `DONE`이면 Backend 예측 완료 API를 호출해 점주 앱 알림(§3.12)을 보내고, `FAILED`(이력 부족 제외)면 Slack 알림 | 로깅만 수행 |

#### 3.11.2 주간 재학습 파이프라인

MVP 제외 기능이다 (`02_implementation_design.md` §1.4).

### 3.12 알림 정책

- 점주 대상 모든 알림은 앱 내 알림(푸시 + 인앱)으로 발송한다.
- 파이프라인 실패 알림은 개발팀 Slack으로 발송한다.

| 알림 상황 | 채널 | 긴급도 |
|---|---|---|
| 이상치 감지 | 앱 내 알림 | 경고 |
| 재고 부족 ("재고 확인 필요") | 앱 내 알림 | 경고 |
| 소비기한 D-3일 임박 | 앱 내 알림 | 경고 |
| 소비기한 D-1일 임박 | 앱 내 알림 | 긴급 |
| 소비기한 초과 폐기 요청 | 앱 내 알림 | 긴급 |
| 예측 완료 | 앱 내 알림 | 정보 |
| 파이프라인 단계 실패 (3회 재시도 후) | Slack (개발팀) | 긴급 |

| 알림 상황 | 발생 시점 | 한 건의 단위 |
|---|---|---|
| 이상치 감지 | CSV 업로드에서 이상치가 1건 이상 | 업로드 한 번 |
| 재고 부족 | CSV 업로드의 재고 차감으로 품목이 '재고 확인 필요'가 새로 됨 | 품목 |
| 소비기한 D-3·D-1·초과 | 소비기한 배치 (§3.3.6) | 품목·조건 |
| 예측 완료 | n8n 야간 배치 완료 (§3.11.1) | 매장 |

- 알림 설정(§4.14)은 소비기한 임박(D-3·D-1·초과)·재고 부족·예측 완료·이상치 감지 네 묶음이고 기본값은 모두 켬이다. 끈 묶음의 알림은 인앱·푸시 모두 만들지 않는다.
- Web Push 발송 실패는 인앱 알림 저장에 영향을 주지 않는다.

## 4. 사용자 흐름

### 4.1 주요 사용자

- 오프라인 식음료 매장 운영자
- 음식점 및 카페 소상공인
- 식자재 재고 관리에 어려움을 겪는 자영업자
- 데이터 기반 경영을 원하지만 IT 역량이 부족한 사용자

### 4.2 핵심 사용 흐름

```text
[공통 시작]
회원가입(이메일)/로그인/소셜 로그인
→ business_status 확인
    ├─ UNVERIFIED·REJECTED → 사업자 검증 화면
    └─ PENDING·VERIFIED → onboarding_completed 확인
                ├─ false → 온보딩 흐름 시작
                └─ true  → 메인 홈

[사업자 검증 (온보딩과 분리된 게이트, 국세청 API 자동 검증 + 관리자 승인 병행)]
사업자등록번호 + 사업자등록증 업로드
→ ① 국세청 API 검증 (마스터 코드면 곧바로 VERIFIED)
    ├─ 미등록/형식 → 재입력 (상태 유지)
    ├─ 휴업/폐업 → 진행 불가, 사유 안내 (상태 유지)
    └─ 계속사업자 → ② 등록증 업로드 → business_status=PENDING → 온보딩 흐름 시작
                      └─ 관리자 심사: 승인 → VERIFIED / 반려 → REJECTED(사유) → 재검증

[관리자 심사 흐름 (role=ADMIN)]
/admin 심사 큐 → PENDING 목록·등록증 확인 → 승인(VERIFIED) 또는 반려(사유 입력→REJECTED)

[온보딩 흐름]
매장 정보 입력
→ POS 연동 방식 선택
    ├─ POS API 성공 → 초기 재고/메뉴 입력 → 메인 홈
    └─ CSV 모드 → 초기 재고/메뉴 입력 → 메인 홈
                (양쪽 모두 수요예측·자동발주 활성화)

[일일 운영 흐름]
메인 홈 접속
→ 수요예측 확인
→ 추천발주 확인
→ 점주 수정/승인
→ 쿠팡 장바구니 자동 담기 시도
    ├─ 전체 성공 → 쿠팡에서 결제 진행
    ├─ 부분 실패 → 성공 품목 담기 완료 + 실패 품목 수동 처리 안내
    └─ 전체 실패 → 전체 품목 수동 처리 안내
```

### 4.3 온보딩 흐름

온보딩 입력 항목 및 POS 상태 기준: §3.1.4

1. 사용자가 이메일 회원가입 또는 Google/카카오 로그인으로 계정을 만든다. → `business_status=UNVERIFIED`
2. 인증 완료 후 `business_status`·`onboarding_completed`를 확인한다. `UNVERIFIED`·`REJECTED`면 사업자 검증 화면으로 이동한다.
3. (검증 게이트, 온보딩과 분리) 사업자등록번호를 입력하면 국세청 API로 즉시 검증한다.
   - 미등록 / 형식 오류 → 재입력 (상태 유지)
   - 휴업 / 폐업 → 진행 불가, 사유 안내 (상태 유지)
   - 계속사업자(또는 마스터 코드) → 사업자등록증 업로드 → `business_status=PENDING` → 온보딩 진행 (관리자 승인 전이라도 진입 가능)
   - 관리자 심사: 승인 → `VERIFIED` / 반려 → `REJECTED`(사유) → 재검증
4. 매장명, 업종, 연락처, 주소, 매장 규모 구간, 운영 형태를 입력한다.
5. POS 연동 방식을 선택한다.
   - CSV 모드 (`pos_connections.status=CSV_MODE`). CSV 템플릿 다운로드와 업로드는 POS 연동 설정 화면에서 한다(§3.4.4).
   - POS API 연동 → POS 종류·자격증명 입력 → 연동 시도
     - 성공: `pos_connections.status=CONNECTED`, "POS 연동 완료" 배지
     - 실패: CSV 모드로 진행 (`status=CSV_MODE`)
   - 양쪽 모두 수요예측·자동발주 추천 활성화
   - 설정 화면에서 모드 전환 가능
6. 초기 재고와 초기 메뉴를 입력한다.
7. 메인 홈 화면으로 이동한다.

중도 이탈 후 재접속 시 마지막 스텝부터 재진입하며, 기존 입력 데이터는 유지된다.

### 4.4 일일 운영 흐름

1. 점주가 메인 홈에 접속한다.
2. 시스템이 저장된 예측 결과와 추천발주안을 조회한다.
3. 점주가 메뉴별 예상 수요를 확인한다.
4. 점주가 품목별 권장 발주 수량과 예상 소진 시점을 확인한다.
5. 점주가 추천 근거와 예측 신뢰도를 확인한다.
6. 점주가 발주 수량 또는 상품을 수정할 수 있다.
7. 점주가 발주를 확정한다.
8. 시스템이 쿠팡 장바구니 자동 담기를 시도한다.
9. 결과에 따라 분기한다. (상세: §4.12)

### 4.5 재고 관리 흐름

1. 점주가 재고 관리 화면에 진입한다.
2. 재고 목록을 확인한다. (기본 정렬: 소비기한 임박순)
3. 신규 입고 시 새 로트를 추가한다 (수량, 입고일, 소비기한, 구매 금액).
4. 기존 로트의 수량 또는 소비기한을 직접 수정할 수 있다. 수정 사유를 필수 입력한다.
5. 폐기할 식자재가 있으면 폐기할 로트를 골라 폐기 수량을 입력한다.
6. 시스템이 폐기 가능 수량을 검증한다.
   - 폐기 가능 → 재고를 차감한다.
   - 폐기 불가 → 오류를 표시한다.

### 4.6 메뉴 관리 흐름

1. 점주가 메뉴 관리 화면에 진입한다.
2. 메뉴 목록을 확인한다.
3. 메뉴를 등록, 수정, 삭제한다.
4. 메뉴 등록 시 메뉴명 중복을 확인한다.
5. 레시피를 저장한 메뉴만 재고 차감을 켤 수 있다.
6. 삭제는 소프트 삭제로 처리된다. 과거 판매 데이터는 유지된다.

### 4.7 판매 데이터 조회 흐름

1. 점주가 판매 데이터 화면에 진입한다.
2. 조회 기간을 선택한다. (최대 1년 범위)
3. 판매 목록을 확인한다. (기본 정렬: 날짜 최신순)
4. 특정 날짜 또는 판매 항목을 선택해 시간대별 판매 내역과 메뉴별 판매 수량 상세를 확인한다.

### 4.8 사용자 통제 흐름

- AI는 추천만 수행한다.
- 점주는 발주 전 추천안을 확인한다.
- 점주는 추천안을 수정할 수 있다.
- 최종 발주 확정은 점주의 명시적 승인으로 수행한다.
- 자동 발주 추천은 자동 결제가 아니다.

### 4.9 대시보드 조회 흐름

1. 점주가 대시보드 화면에 진입한다.
2. 기본 조회 기간(주별)의 데이터가 자동으로 표시된다.
3. 조회 기간을 변경하며 아래 지표를 확인한다.
   - 기간별 매출 추이 (선 그래프)
   - 메뉴별 판매 비중 (도넛 차트)
   - 수요예측 vs 실제 판매량 비교 (선 그래프)

### 4.10 소비기한 관리 흐름

소비기한 알림 기준: §3.3.6

1. 야간 배치(01:30)에서 전체 로트의 소비기한을 자동 체크한다.
2. 조건에 따라 분기한다.
   - D-3일 임박: 경고 알림 발송 + 재고 목록에 경고 배지 표시
   - D-1일 임박: 긴급 알림 발송 + 재고 목록에 긴급 배지 표시
   - 소비기한 초과: 폐기 요청 알림 발송 (자동 폐기 없음)
3. 점주가 알림을 확인하고 재고 관리 화면으로 이동한다.
4. 해당 로트를 선택하고 폐기 처리를 수행한다.
   - 폐기 가능 수량 충족 → 재고 차감
   - 수량 부족 → 오류 표시

### 4.11 알림 수신 흐름

알림 채널 및 긴급도 기준: §3.12

1. 알림 발생 시 점주의 앱으로 푸시 알림이 발송된다.
2. 앱 접속 시 홈 화면의 경고 배지 영역에 활성 알림이 우선순위 순으로 표시된다.
   - 우선순위: 긴급 → 경고 → 정보
3. 알림 항목을 탭하면 해당 기능 화면으로 이동한다.

| 알림 상황 | 이동 화면 |
|---|---|
| 재고 부족 ("재고 확인 필요") | 재고 관리 |
| 소비기한 D-3 / D-1 임박 | 재고 상세 |
| 소비기한 초과 폐기 요청 | 재고 상세 |
| 이상치 감지 | 판매 데이터 |
| 예측 완료 | 추천발주 |

4. 설정 > 알림 설정에서 알림 유형별 on/off를 변경할 수 있다.

### 4.12 쿠팡 자동화 실패 분기 흐름

실패 처리 정책 기준: §3.8.2

1. 점주가 발주를 확정하고 자동 담기를 요청하면 사주라 확장이 쿠팡 장바구니 담기를 시도한다.
2. 결과(전체 성공 / 부분 실패 / 전체 실패)에 따라 §3.8.2 처리로 분기한다. 재시도 없이 실패 즉시 수동 처리를 안내한다.
3. 점주가 쿠팡 앱/웹에서 실패 품목을 직접 처리한다.

### 4.13 리드타임/안전재고 설정 흐름

기본값 및 `DEFAULT_USED` 상태 기준: §3.7.1

1. 점주가 재고 관리 화면에서 재료를 선택한다.
2. 재료 상세 화면에서 리드타임(일 단위)과 안전재고를 입력하고 저장한다.
3. 저장된 값은 다음 추천발주 생성 시 반영된다.
4. 미설정 재료는 시스템 기본값을 사용하며 `DEFAULT_USED` 상태로 설정 필요 안내를 표시한다.

### 4.14 설정 관리 흐름

1. 점주가 하단 네비게이션 바 > 설정 화면에 진입한다.
2. 항목별 흐름:

| 항목 | 흐름 |
|---|---|
| POS 연동 관리 | 현재 연동 상태 확인 → POS 재연동 시도 또는 CSV 업로드 선택 |
| 알림 설정 | 알림 유형별 on/off 토글 (소비기한 임박 / 재고 부족 / 예측 완료 / 이상치 감지) |
| 계정 정보 | 매장 정보 수정 / 로그아웃 / 회원 탈퇴 (보유 기간 규칙: §5.2.1) |
| 앱 정보 | 앱 버전, 이용약관, 개인정보처리방침 확인 |

## 5. 비기능 요구사항

### 5.1 보안

- 동의 기반 최소 데이터 수집을 적용한다 (§5.2).
- AI는 추천하고, 결정과 실행은 사용자가 한다.
- 자동 발주와 자동 결제를 분리한다.
- 매출 데이터와 결제 정보는 민감 정보로 보호한다.
- OAuth 제공자의 access/refresh token은 저장하지 않고 자체 JWT를 발급한다.

| 항목 | 정의 위치 |
|---|---|
| 인증·토큰 (bcrypt, Refresh Token 해시 저장) | `03_be.md` §7 |
| 접근 통제 (`store_id` 소유권 검증, 역할 구분) | `03_be.md` §8 |
| 감사 로그 | `03_be.md` §9 |
| 저장·전송 암호화 (AES-256-GCM, TLS 1.3) | `03_be.md` §10, 대상 컬럼 `02_implementation_design.md` §4.6 |
| DB 계정 분리·직접 접근 경로 (VPN 또는 배스천 호스트) | `02_implementation_design.md` §4.5, `03_be.md` §8.2 |
| 결제 정보 미저장 | §6.2 |

### 5.2 개인정보 보호

- 회원가입 시 수집 항목, 이용 목적, 보유 기간을 명시한다.
- 필수 항목과 선택 항목을 분리해 동의를 받는다.
- 모델 학습에 필요한 최소 데이터만 수집한다.
- 불필요한 정보는 수집 단계에서 차단한다.
- 매장 식별자는 모델 학습 시 해시 처리한다.
- 학습용 데이터는 집계화하여 활용한다.
- 원본 매출 데이터는 점주 본인 계정으로만 접근 가능해야 한다.
- 운영진은 원본 매출 데이터를 조회할 수 없어야 한다. 개발자는 마스터 계정 `dev_master`로만 DB에 직접 접근한다(`02_implementation_design.md` §4.5).

#### 5.2.1 개인정보 수집 항목

필수 수집 항목 (회원가입·온보딩)

| 항목 | 수집 목적 |
|---|---|
| 이메일 | 계정 식별, 알림 발송 |
| 사업자등록번호 | 국세청 API 계속사업자 검증 |
| 매장명, 업종, 연락처, 주소 | 매장 운영 및 AI 예측 지역 변수 활용 |
| 매장 규모 구간, 운영 형태 | Cold-start 유사 매장 매칭 기준 |

서비스 이용 중 수집

| 항목 | 수집 목적 |
|---|---|
| POS API 자격증명 | POS 연동 인증 (AES-256-GCM 암호화 저장) |
| 판매 데이터 | 수요예측 모델 학습·추론 입력 |
| 재고 입력 데이터 | 추천발주 산출 기준 |

|---|---|

| GPS·위치 정보 | 실시간 위치 미수집. 주소에서 변환한 좌표만 날씨 조회에 쓴다 |

보유 기간

- 서비스 이용 기간 동안 보유한다.
- 회원 탈퇴 요청 시 `users.withdrawn_at`을 기록하고 모든 Refresh Token을 폐기한다. 이때부터 로그인(이메일·소셜)과 매장 데이터 API를 차단하고, 탈퇴 철회는 받지 않는다.
- 유예 기간 동안 같은 이메일·소셜 계정으로 재가입할 수 없다.
- 회원 탈퇴 후 30일 유예 기간 경과 시 백업 포함 완전 파기한다. 매일 03:00 ARQ 배치가 `withdrawn_at`으로부터 30일이 지난 계정을 매장 데이터·사업자등록증 파일과 함께 삭제한다.
- 파기 완료 시 이메일로 증빙을 발송한다.

### 5.3 성능

- 사용자 요청 시 수요예측과 추천발주 결과를 빠르게 반환한다.
- AI 추론 지연이 사용자 응답 시간에 직접 영향을 주지 않도록 한다. AI 예측은 사전 배치 계산 후 DB에 저장하고, 사용자 요청 시 DB 조회를 우선 수행한다.
- 저장된 예측 결과가 없을 때만 수동 실행으로 그 매장의 예측 워크플로우를 즉시 실행한다.
- 매장 수 증가와 데이터 누적에 따른 처리 비용을 통제한다.

## 6. 제약과 외부 정책

### 6.1 제약 조건

- 최종 발주 확정은 반드시 점주 승인 단계를 거쳐야 한다.
- 추천 발주 사이트는 쿠팡 단일로 한정한다. 장바구니 자동 담기: §3.8 / 단가 조회: §3.3.1.
- 공급업체 평가 기능은 사주라 전체 로드맵 범위 밖이다.
- 자동 발주 트리거는 점주가 발주 확정 후 명시적으로 자동화 버튼을 눌러야 실행된다 (§3.8, `03_be.md` §6).

### 6.2 결제 및 외부 거래

- 실제 결제는 쿠팡에서 진행한다. 사주라는 브라우저 확장으로 점주 브라우저의 쿠팡 장바구니에 품목을 담을 뿐 결제 단계는 점주가 쿠팡에서 직접 수행한다 (§3.8).
- 쿠팡 자격증명을 수집·저장하지 않는다. 담기는 점주 브라우저에서 수행하므로 서버가 쿠팡 계정에 접근하지 않는다. 확장이 서버로 보내는 쿠팡 화면 요소 목록은 회원 이름·전화번호·이메일·주소를 `---`로 가린 뒤 보낸다 (`04_fe.md` §12.4).
- 카드·결제수단 정보는 사주라 서버를 경유하지 않고, 저장하지도 않는다.
- 사주라 서버에는 결제 관련 토큰·식별자를 보관하지 않는다 (PG 연동 없음).
- 일정 금액 이상의 발주에 대한 추가 인증은 쿠팡 결제 단계에서 쿠팡 정책에 따라 처리된다.

### 6.3 외부 API 및 약관

- 외부 인터페이스는 REST API, JSON, OAuth 2.0 표준을 채택한다.
- POS 사업자의 공식 OAuth 2.0 기반 API만 사용해야 한다.
- 승인된 scope 이내로만 데이터를 요청해야 한다.
- API 호출 throttling을 적용해야 한다.
- 외부 라이브러리는 라이선스를 검토해야 한다.

### 6.4 사용자 권리

- 회원 탈퇴와 데이터 파기는 §5.2.1 보유 기간 규칙을 따른다.
