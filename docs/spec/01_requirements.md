# 요구사항 정의서

## 1. 프로젝트 개요

사주라(Sajura)는 소상공인을 위한 AI 기반 자동발주 및 매출분석 솔루션이다.

목표는 재고/발주의 의사결정을 데이터 기반으로 자동화하고, 매출 분석을 통해 매장 운영 인사이트를 제공하는 것이다.

## 2. 해결하려는 문제

### 2.1 수작업 재고 관리

- 소상공인 70%가 수기 또는 엑셀로 재고를 관리한다.
- 인적 오류와 시간 낭비가 발생한다.

### 2.2 감에 의존한 발주

- 과거 경험과 감각에 의존해 발주한다.
- 과잉재고 또는 결품이 빈번하게 발생한다.

### 2.3 매출 분석의 부재

- 날씨, 요일, 시즌 등 외부 변수가 매출에 미치는 영향을 파악하지 못한다.
- POS, 재고, 발주 데이터가 분리되어 빠른 판단이 어렵다.

## 3. 핵심 고객

| 고객 세그먼트 | 설명 |
|---|---|
| 음식점 및 카페 소상공인 | 식자재 회전율이 높고 일일 발주가 필요한 개인 매장 |
| 소규모 프랜차이즈 매장 | 본사 물류 외에 개별 식자재 관리가 필요한 가맹점 |
| 직접 관리하는 자영업자 | 전담 관리 직원 없이 점주가 직접 재고 관리와 발주를 수행하는 매장 |

개발 최우선 대상은 음식점 운영 소상공인이다.

## 4. 가치 제안

"처음 한 번만 재고를 입력하세요. 이후의 재고 관리와 발주 판단은 AI가 모두 대신합니다."

## 5. 기능 요구사항

### 5.1 회원가입 및 인증

- 사용자는 Google 또는 카카오 계정으로 회원가입 및 로그인할 수 있어야 한다.
- Google과 카카오 OAuth 2.0 흐름은 Backend에서 Authlib를 사용해 처리한다.
- Frontend는 소셜 로그인 버튼 클릭 시 Backend의 인가 URL로 리다이렉트한다.
- Backend는 OAuth 콜백에서 사용자 정보를 조회하고 자체 JWT Access Token과 Refresh Token을 발급한다.
- 사용자는 이메일/비밀번호 방식으로도 회원가입 및 로그인할 수 있어야 한다.
- 비밀번호는 bcrypt로 해시하여 저장한다.
- 모든 인증 방식은 동일한 자체 JWT 구조를 사용한다.
- 회원가입 후 사용자는 온보딩에서 사업자등록번호, 매장 정보, POS 연동, 초기 재고, 초기 메뉴를 입력해야 한다.
- POS API 연동 [2단계] 실패 시 CSV 임시 모드로 진행할 수 있다. CSV 모드에서도 수요예측·자동발주 추천 기능은 동일하게 동작한다 (`mvp_scope.md` §3·§6).
- 온보딩 미완료 사용자는 로그인 응답의 `onboarding_completed: false` 값을 기준으로 초기 설정 화면으로 이동해야 한다.

### 5.2 POS 연동

- POS 데이터는 CSV 또는 API 방식으로 연동한다.
- POS별 데이터 형식 차이를 처리하기 위해 공통 중간 스키마와 어댑터 패턴을 적용한다.
- 지원 대상 어댑터는 TossPlaceAdapter, KiwoomAdapter, OKPOSAdapter, CSVAdapter이다.
- 입력 데이터는 JSON Schema 또는 Pydantic으로 검증해야 한다.
- 이상치 탐지를 수행한다 (탐지 방법·임계값·이상 데이터 처리 정책은 별도 확정 예정).

### 5.3 메뉴 및 레시피 관리

- 점주는 메뉴를 등록, 조회, 수정, 삭제할 수 있어야 한다.
- 메뉴명 중복 검증을 수행해야 한다.
- 메뉴는 재고와 직접 연결되지 않고 레시피를 통해 재료항목과 연결되어야 한다.
- 레시피는 메뉴별 재료 사용량을 관리해야 한다.

### 5.4 재고 관리

- 점주는 초기 재고를 등록할 수 있어야 한다.
- 판매된 메뉴의 레시피를 기반으로 식자재 사용량이 자동 계산되어야 한다.
- 현재 재고가 자동 추적되어야 한다.
- 점주는 재고를 조회하고 수정할 수 있어야 한다.
- 점주는 재고 폐기 처리를 요청할 수 있어야 한다.
- 서버는 폐기 처리 전 현재 수량을 검증해야 한다.
- 폐기 가능 수량이 충분한 경우에만 재고를 차감해야 한다.
- 소비기한 자동 관리 및 알림을 제공한다. (D-3·D-1·초과 알림 정책: `feature_spec.md` §5)

### 5.5 판매 데이터 조회

- 점주는 기간을 선택해 판매 데이터를 조회할 수 있어야 한다.
- 점주는 판매 목록과 상세 판매 데이터를 확인할 수 있어야 한다.

### 5.6 수요예측

- 시스템은 과거 매출, 날씨, 요일/공휴일, 지역 이벤트 데이터[조사 중], SNS 노출도[조사 중]를 반영해 메뉴별 1-3일 예상 수요를 예측해야 한다.
- AI Server는 주기적 배치 예측 요청에 대해 수요예측 결과를 생성해야 한다.
- 예측 결과는 DB에 사전 저장되어 사용자 요청 시 즉시 반환되어야 한다.
- 저장된 예측 결과가 없고 수동 실행이 허용된 경우 Backend는 AI Server를 호출해 단건 예측을 수행할 수 있다.
- 예측 결과에는 점주가 이해할 수 있는 근거가 제공되어야 한다 (산출 방법·출력 형태는 별도 확정).
- 예측 신뢰도가 낮은 경우 경고 배지를 표시해야 한다.

### 5.7 추천발주

- AI Server는 예측 판매량, 현재 재고, 레시피 소모량, 리드타임, 안전재고를 반영해 품목별 권장 발주 수량을 생성해야 한다.
- AI Server는 예상 소진 시점을 제안해야 한다.
- n8n은 AI Server가 생성한 추천발주 결과를 DB에 사전 저장해야 한다.
- 점주는 추천발주안을 확인, 수정, 승인할 수 있어야 한다.
- 점주 수정 이력과 실제 판매 결과는 다음 추천 정확도 개선에 반영되어야 한다.

### 5.8 발주 실행 보조

- 점주가 발주를 승인하면 발주 기록을 저장해야 한다.
- Backend는 Playwright를 통해 쿠팡 장바구니 자동 담기를 수행해야 한다.
- 실제 결제는 쿠팡에서 진행된다.
- 자동 발주와 자동 결제는 분리되어야 한다.

### 5.9 매출 분석 및 대시보드

- Frontend는 매출 및 예측 결과를 통합 대시보드로 시각화해야 한다.
- ROI 대시보드는 기간별 폐기율, 재고 회전율, 예측 정확도 지표(지표 선정은 별도 확정), 월별 폐기 비용 및 전월 대비 폐기 비용 변화율을 제공해야 한다.

## 6. 비기능 요구사항

### 6.1 보안

- 회원가입 시 수집 항목, 이용 목적, 보유 기간을 명시해야 한다.
- 필수 항목과 선택 항목을 분리해 동의를 받아야 한다.
- 비밀번호는 bcrypt로 해시하여 저장한다.
- POS API 키 등 외부 서비스 자격증명은 AES-256-GCM(애플리케이션 레벨)으로 암호화하여 저장한다. OAuth 외부 access/refresh token은 사주라 BE가 저장하지 않으며 자체 JWT를 발급한다 (`security.md` §2.1).
- Refresh Token은 해시값만 저장하며 원문은 보관하지 않는다.
- 전송 구간은 HTTPS(TLS 1.3)를 적용한다. (정책 상세: `security.md` §4)
- API 접근은 점주 단일 역할 기반으로 store_id 소유권 검증을 적용하여 다른 매장 데이터 접근을 차단한다.
- 감사 로그는 인증 실패, 계정 변경, 재고 수동 조정, 폐기 처리, 발주 확정, n8n 배치 쓰기 작업 중심으로 기록한다.
- DB 직접 접근은 역할별 전용 계정으로 분리하며 VPN 또는 배스천 호스트를 경유한다.
- 실제 결제는 쿠팡에서 진행되며, 카드 및 결제 정보는 자체 서버를 거치지 않아 저장하지 않는다.
- 추후 직원 계정 또는 관리자 계정이 추가될 경우 RBAC 기반 역할 분리 설계로 확장한다.

### 6.2 성능

- AI 예측은 사전 배치 계산 후 DB에 저장해야 한다.
- 사용자 요청 시 DB 조회를 우선 수행하여 응답 지연을 줄여야 한다.
- 저장된 예측 결과가 없을 때만 수동 실행 보조 흐름에서 AI Server를 직접 호출할 수 있다.

### 6.3 확장성 및 유지보수성

- Backend는 Controller / Service / Model 3계층 구조를 적용해야 한다.
- POS 연동은 공통 스키마와 어댑터 패턴으로 확장 가능하게 설계해야 한다.
- ML 서버와 Backend 서버는 분리 배포한다.
- GitHub Actions를 통한 CI/CD 자동화를 적용한다.

### 6.4 운영

- n8n은 배치 워크플로우의 실행 주체이다.
- n8n은 매일 02:00 야간 예측/추천발주 워크플로우를 트리거한다.
- n8n은 DB에서 판매 데이터, 메뉴, 레시피, 재고, 리드타임, 안전재고, 기존 예측/발주 이력을 직접 조회한다.
- n8n은 날씨, 유동인구, 검색량[조사 중], 행사 정보[조사 중] 등 외부 데이터를 API로 수집한다.
- n8n은 수집한 DB/API 데이터를 AI Server 입력 스키마에 맞게 전처리 및 정규화한다.
- n8n 전처리에는 결측값 처리, 이상치 필터링, 단위 통일, 날짜/시간 기준 정렬, 메뉴/재료 매핑, 외부 변수 병합이 포함된다.
- n8n은 전처리 및 정규화한 입력 데이터를 AI Server에 전달한다.
- AI Server는 수요예측과 추천발주 생성을 수행한다.
- n8n은 AI Server가 반환한 예측 결과와 추천발주 결과를 DB에 직접 저장한다.
- n8n은 `pipeline_jobs`에 실행 시작/종료 상태와 실패 사유를 직접 기록한다.
- Backend는 점주용 조회/수정/승인 API와 수동 실행 보조 기능을 담당한다.
- 실패 시 n8n 재시도 정책에 따라 단계별 재시도 후 Slack 알림을 제공한다.
- 실행 결과 모니터링 대시보드를 제공한다.

## 7. 제약 조건

- AI는 추천하고, 결정과 실행은 사용자가 한다.
- 최종 발주 확정은 반드시 점주 승인 단계를 거쳐야 한다.
- 추천 발주 사이트는 쿠팡 단일로 한정한다. Playwright 자동화 및 단가 조회: `feature_spec.md` §9.
- 공급업체 평가 기능은 사주라 범위 외이다 (`mvp_scope.md` §4 MVP 제외 기능 외에도 전체 로드맵 범위 밖).
- 자동 발주 트리거는 점주가 발주 확정 후 명시적으로 자동화 버튼을 눌러야 실행된다 (`feature_spec.md` §9, `service_design.md` §6).
