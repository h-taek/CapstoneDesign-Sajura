## 7. 인증·토큰

### 7.1 소셜 로그인 (Google / 카카오)

인증 흐름은 `01_basic_design.md` §3.1.1에 둔다.

- Google과 카카오 모두 Authlib으로 Backend에서 OAuth 2.0 흐름을 처리한다. Firebase SDK를 쓰지 않는다.
- Frontend는 로그인 버튼 클릭 시 Backend의 인가 URL(`GET /api/auth/login/google`, `GET /api/auth/login/kakao`)로 리다이렉트만 수행한다.
- Backend 콜백에서 사용자 정보를 조회하고 자체 JWT를 발급한다.
- 인증 제공자와 무관하게 동일한 자체 JWT 구조를 사용한다.

### 7.2 이메일/비밀번호 로그인

- 비밀번호는 bcrypt로 해시하여 저장한다. 원문은 저장하지 않는다.
- 소셜 로그인 계정은 비밀번호 변경 기능을 사용할 수 없다.

### 7.3 토큰 정책

토큰 DB 스키마는 `02_implementation_design.md` §4.3.2, JWT payload는 §8.1이다.

- Access Token(JWT)은 서명 검증만으로 인증한다(DB 조회 없음). `user_id`, `store_id`, 만료 시각을 포함한다.
- Refresh Token은 Access Token 갱신 전용이다. API 요청에 직접 사용하지 않는다.

Access Token

| 항목 | 내용 |
|------|------|
| 유효기간 | 1시간 |
| 저장 위치 | Frontend 메모리 (LocalStorage 저장 금지) |
| 만료 시 | 401 반환 → Frontend가 자동으로 Refresh Token 갱신 요청 후 원래 요청 재시도 |

Refresh Token

| 항목 | 내용 |
|------|------|
| 유효기간 | 30일 |
| 저장 위치 | HttpOnly Cookie `refresh_token` (HttpOnly · Secure · SameSite=Lax, JavaScript 접근 불가) |
| DB 저장 방식 | 원문 미저장, SHA-256 해시값(`token_hash`)만 저장 |
| Rotation 정책 | 사용마다 새 토큰으로 교체, 기존 토큰 즉시 폐기(`is_revoked: 1`) |
| 만료/폐기 시 | 401 반환 → 로그인 화면 이동 |

로그아웃

- Refresh Token을 DB에서 `is_revoked: 1`로 즉시 폐기한다.
- HttpOnly Cookie에서 제거한다.
- 블랙리스트 캐시 등록은 §12.

다중 디바이스 로그인

각 디바이스(PC·모바일 등)는 자체 Refresh Token을 발급받아 독립 Rotation 흐름을 유지한다. 한 디바이스의 Rotation·로그아웃은 다른 디바이스에 영향을 주지 않는다. `refresh_tokens` 테이블에서 user_id가 같고 token_hash가 다른 행으로 구분한다.

강제 로그아웃 (모든 디바이스)

점주가 `POST /api/auth/logout-all`을 호출하면 해당 user_id의 활성 `refresh_tokens` 전체를 `is_revoked: 1`로 일괄 폐기한다. Access Token은 자체 무효화하지 않으므로, 최대 1시간(Access Token 유효기간) 이내 모든 디바이스가 401 응답을 받고 재로그인으로 이동한다.

### 7.4 사업자 검증 마스터 코드

`POST /api/store/business/verify`에서 입력 `business_no`가 환경변수 `NTS_MASTER_BYPASS_CODE`와 일치하면 국세청 호출·등록증 업로드·관리자 승인을 모두 건너뛰고 곧바로 `business_status=VERIFIED`로 만든다(시연·데모·로컬 테스트용 의도적 백도어). 다음을 강제한다.

- 운영(production) 환경에서는 `NTS_MASTER_BYPASS_CODE`를 빈 값으로 둔다. 빈 값이면 마스터 패스가 비활성이고 어떤 입력도 우회할 수 없다.
- 코드 값은 시크릿으로 취급한다(소스·문서·로그에 평문 노출 금지). `.env`에만 보관하고 git에 커밋하지 않는다.
- 마스터 코드로 통과한 매장은 시연 계정에만 사용한다(운영 데이터와 분리).

## 8. 권한·접근 통제

### 8.1 애플리케이션 접근 통제

- `users.role`로 점주(`OWNER`)·관리자(`ADMIN`) 2역할을 구분한다. ADMIN은 운영자 계정만 DB에서 수동 지정한다(가입 경로로 ADMIN 부여 불가).
- 점주 API: JWT payload의 `store_id`를 요청 대상 데이터의 `store_id`와 대조하고, 불일치 시 403 `FORBIDDEN`을 반환한다.
- 매장 데이터 API: `stores.business_status`가 `PENDING`·`VERIFIED`이고 탈퇴 유예 중이 아닐 때만 통과, 그 외 403 `BUSINESS_NOT_VERIFIED`. 대상은 메뉴·재고·판매·발주·예측·POS·단가 API와 매장 정보 수정·온보딩 완료다. 인증·매장 조회·사업자 검증 요청은 제외한다. 상태는 요청마다 DB에서 조회해 관리자 반려가 발급된 토큰에도 즉시 반영된다 (`01_basic_design.md` §3.1.4).
- 관리자 API(`/api/admin/*`): `role=ADMIN`만 통과, 그 외 403. 사업자 검증 심사·등록증 파일 조회에 한정한다.
- `role`은 JWT에 넣지 않고 `/api/admin/*` 진입 시 DB에서 조회·확인한다.

> 기준: `01_basic_design.md` §5.1

#### 검사 레벨

| 레벨 | 설명 | 적용 위치 |
|------|------|-----------|
| 인증 확인 | Access Token 유효성 검증 | 모든 보호 endpoint |
| 소유권 확인 | 요청 리소스가 자신의 매장 소속인지 검증 | 리소스 조회/수정/삭제 시 |
| 계정 타입 확인 | LOCAL 계정 전용 기능 제한 (§7.2) | `change_password` |

#### JWT payload

```json
{
  "sub": "user_id",
  "store_id": "uuid",
  "exp": 1234567890
}
```

소유권 확인은 DB 조회 없이 payload의 `store_id`로 한다.

#### 소유권 확인 방식

```
요청 수신
  → Access Token 디코딩 → store_id 추출
  → 리소스의 store_id == token.store_id 확인
  → 불일치 시 403 FORBIDDEN 반환
```

#### 리소스별 소유권 확인 대상

| 리소스 | 확인 방법 |
|--------|-----------|
| `menus`, `recipes` | `menus.store_id == token.store_id` |
| `inventory_items`, `inventory_lots` | `inventory_items.store_id == token.store_id` |
| `sale_records` | `sale_records.store_id == token.store_id` |
| `orders`, `order_items` | `orders.store_id == token.store_id` |
| `forecast_results` | `forecast_results.store_id == token.store_id` |
| `pipeline_jobs` | `pipeline_jobs.store_id == token.store_id` |

## 10. 암호화

- 백업 데이터에도 동일 암호화 정책을 적용한다.
- 전송 구간에는 TLS 1.3을 적용한다.
- TLS 종료는 외부 엣지(Caddy v2)에서 수행한다. 내부 BE upstream은 HTTP/1.1 평문이며 같은 호스트 또는 컨테이너 네트워크 내부로 한정한다. (구성: §1, `docs/research/backend/03_reverse_proxy.md` §4)

### 10.1 저장 암호화 적용 대상

적용 대상 컬럼과 방식은 `02_implementation_design.md` §4.6에 둔다. 적용 기준은 유출 시 외부 서비스에 직접 피해를 줄 수 있는 자격증명, 또는 원문 복구가 불가능해야 하는 값이다.

AES-256-GCM 키는 환경변수 `AES_GCM_KEY_BASE64`(32바이트 base64)로 주입한다. 암호문은 행마다 새 nonce를 쓰고 소유 매장의 `store_id`를 연관 데이터로 묶어, 다른 매장 행으로 옮기면 복호화되지 않는다. API 응답에는 복호화한 값을 앞 2자·뒤 2자만 남기고 마스킹한다.

암호화하지 않는 항목

| 항목 | 비고 |
|------|------|
| 이메일, 매장명 등 식별 필드 | 검색·조회가 필요한 필드 |
| 판매 데이터, 재고 데이터 | 집계·분석이 빈번한 데이터 |

### 10.2 사업자등록증 파일 보관

업로드된 사업자등록증(이미지/PDF)은 민감정보다. 원본은 DB에 넣지 않고 서버 볼륨(컨테이너 외부 마운트)에 파일로 저장하고 `stores.business_cert_path`에 경로만 둔다.

- 파일은 웹 루트·정적 서빙 경로 밖에 둔다(직접 URL 접근 불가).
- 조회는 `GET /api/admin/verifications/{store_id}/cert` 단일 경로로만, ADMIN 가드 통과 시에만 스트리밍한다.
- 업로드는 형식(image/*·application/pdf)·용량 제한을 검증한다(`python-multipart`).
- 회원 탈퇴 파기 시 등록증 파일도 함께 삭제한다(`01_basic_design.md` §5.2.1 보유 기간).

## 12. 캐시 계층

| 캐시 키 패턴 | 캐시 대상 | TTL | 무효화 시점 | 전략 |
|-------------|-----------|-----|------------|------|
| `forecast:{store_id}:{target_date}` | 수요예측 결과 | 24시간 | 새 예측 실행 시 | Cache-Aside |
| `recommend:{store_id}` | 최신 추천발주 | 24시간 | 점주 수정 또는 새 추천 생성 시 | Cache-Aside |
| `dashboard:{store_id}` | 대시보드 요약 | 10분 | 자동 만료 | TTL 기반 |
| `inventory_summary:{store_id}` | 재고 현황 요약 | 5분 | 자동 만료 | TTL 기반 |
| `refresh_token_blacklist:{token_hash}` | 무효화된 Refresh Token | 30일 | 로그아웃/탈퇴 시 등록 | Write-Through |

Cache-Aside (수요예측/추천발주)
```
읽기: Redis 확인 → MISS면 DB 조회 → Redis 저장 → 반환
쓰기: DB 저장 → Redis 키 삭제 (다음 읽기 때 재적재)
```

TTL 기반 (대시보드/재고 요약)
```
저장: Redis에 TTL 설정하여 저장
읽기: TTL 내면 캐시 반환, 만료 후 DB 재조회
```
집계 데이터는 10분 이내 오차를 허용한다.

Write-Through (Refresh Token 블랙리스트)
```
로그아웃/탈퇴 시: Redis에 token_hash 즉시 등록
토큰 검증 시: Redis 블랙리스트 확인 → 존재하면 401 반환
```

## 13. 미들웨어

### 13.1 등록 순서

요청은 가장 바깥(보안·호스트) → 컨텍스트(요청 ID) → 관측(에러 추적) → 인증 → 라우터 순으로 미들웨어를 거친다.

```
요청 →
  1. CORSMiddleware (FastAPI 내장)
  2. TrustedHostMiddleware (Starlette 내장)
  3. asgi-correlation-id (X-Request-ID 처리·UUID 부여)
  4. sentry-sdk[fastapi] 자동 통합 (예외·트랜잭션 추적)
  5. SessionMiddleware (Starlette 내장, OAuth state 서명 쿠키 `oauth_session` — 10분, `SESSION_SECRET`으로 서명)
  6. 인증 의존성 (FastAPI Depends)
  7. 라우터
```

### 13.2 CORS 정책

| 항목 | 값 |
|------|---|
| `allow_origins` | 운영 PWA 도메인(`<sub>.iptime.org`) + 개발 환경(`localhost:5173` 등 환경별 `.env`로 주입) |
| `allow_credentials` | `True` (Refresh Token HttpOnly Cookie 흐름) |
| `allow_methods` | `["*"]` |
| `allow_headers` | `["*"]` |

### 13.3 TrustedHost 정책

| 항목 | 값 |
|------|---|
| `allowed_hosts` | `["<sub>.iptime.org", "localhost", "be"]` (Caddy 내부 hostname `be` 포함) |

### 13.4 Rate Limit 정책

| 대상 endpoint | 제한 | 키 |
|------------|------|---|
| `POST /api/auth/login` · `POST /api/auth/register` | 5/min | IP 기반 |
| `POST /api/auth/refresh` | 30/min | IP 기반 |
| `POST /api/notifications/subscribe` | 10/min | `user_id` |
| `GET /api/notifications` | 60/min | `user_id` |
| 그 외 일반 API | 미적용 | — |

## 14. 성능 전략

성능 목표 수치는 `01_basic_design.md` §5.3에 둔다.

### 14.1 핵심 전략

#### 14.1.1 배치 예측

- AI예측시스템은 주기적으로 배치 예측을 수행한다.
- 사전 예측 결과 및 추천발주안을 DB에 저장한다.
- 사용자 요청 시 DB 조회를 우선 수행한다.

#### 14.1.2 캐싱

- 예측 결과는 DB에 저장하여 즉시 응답에 대비한다.
- 저장된 예측 결과가 없을 경우에만 AI Server를 직접 호출한다.
- 수요예측·추천발주·대시보드·재고 요약은 Redis에 캐싱한다. 대상·TTL·무효화 시점·전략은 §12.

#### 14.1.3 야간 배치

### 14.4 모니터링

- n8n 실행 결과 모니터링 대시보드를 제공한다.
- BE 운영 시 응답 시간·에러율·DB 쿼리 시간을 모니터링한다.
- 구조화 로깅(stdout JSON)은 structlog + asgi-correlation-id로 처리한다. 필수 필드: `ts`(UTC ISO), `level`, `event`, `request_id`, `user_id`, `store_id`, `path`, `method`, `status`, `duration_ms`.
- BE 에러·성능 추적은 Sentry SDK(sentry-sdk[fastapi])를 사용한다. PII scrubbing 활성, `traces_sample_rate=0.1`(prod), `environment` 분리, Release tagging은 Git commit SHA 환경변수 주입.
- FE 에러·성능 추적은 `04_fe.md` §9.
- 메트릭 수집(Prometheus)·분산 트레이싱(OpenTelemetry)은 MVP에서 채택하지 않는다. 매장 300+·BE 노드 2+·Sentry 이벤트 한도 초과 중 하나를 충족하면 도입한다.

## 15. 운영 토폴로지

### 15.1 컨테이너 구성 (Docker Compose V2)

단일 `docker-compose.yml`에 6 서비스를 정의한다. 환경 override 파일(`docker-compose.staging.yml`·`docker-compose.prod.yml`)로 staging·prod를 분리한다.

| 서비스 | 이미지 | 역할 |
|--------|------|------|
| `be` | 자체 빌드 (Gunicorn + uvicorn.workers) | FastAPI BE 본체 |
| `arq-worker` | 자체 빌드 (`arq <module>.WorkerSettings`) | 잡 큐 + cron_jobs 실행 |
| `mysql` | `mysql:8` | DB (`02_implementation_design.md` §4.1) |
| `redis` | `redis:7-alpine` | 캐시 + 잡 큐 브로커 + Rate Limit |
| `n8n` | `n8nio/n8n` | AI 파이프라인 오케스트레이션 |
| `caddy` | 자체 빌드 (`Dockerfile.caddy` — `caddy:2-alpine` 베이스 + FE `dist/` COPY) | 리버스 프록시 + 자동 HTTPS + PWA 정적 파일 서빙. FE Vite 빌드 산출을 이미지에 포함하여 atomic 배포·롤백. 상세: `docs/research/frontend/10_deployment.md` §3.4 |

> AI Server는 §14.1.5 분리 배포에 따라 이 Compose 외부에 별도 배포한다. 운영 환경 메모리 할당은 `01_basic_design.md` §5.3.3.

### 15.2 환경 분리

| 환경 | 실행 |
|------|------|
| 로컬 개발 | `uv run uvicorn main:app --reload` + Compose는 MySQL·Redis만 |
| 스테이징 | `docker compose -f docker-compose.yml -f docker-compose.staging.yml up` (`.env.staging`) |
| 운영 | `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` (`.env.prod`) |

시크릿은 환경별 `.env.*` 파일 + Docker secret 마운트로 주입한다. 운영 비밀은 Git에 커밋하지 않는다(`.gitignore` 강제).

### 15.3 CI 파이프라인 (GitHub Actions, 8단계)

```
1. checkout
2. uv sync --frozen              (의존성 잠금 검증)
3. pre-commit run --all-files    (ruff check + format + mypy + bandit + pip-audit)
4. pytest --cov                  (단위 + 통합, testcontainers Docker 필요)
5. docker buildx build           (linux/amd64,linux/arm64 멀티 아키)
6. trivy image <built-image>     (SARIF → GitHub Security 통합)
7. (main 브랜치) GHCR push
8. (main 브랜치) 운영 호스트 pull-and-restart
```

| 단계 | 실패 처리 |
|------|--------|
| 2 · 3 · 4 · 6 | PR 머지 차단 |
| 5 | 단일 아키 재시도 후에도 실패 시 차단 |
| 7 · 8 | 이전 이미지 태그로 롤백 |

### 15.4 이미지 태그 정책

| 환경 | 태그 |
|------|---|
| 운영 | `git-<commit-sha-short>` + `prod-latest` |
| 스테이징 | `git-<commit-sha-short>` + `staging-latest` |
| 개발 | `dev-<branch>-<commit-sha-short>` |

Sentry Release tagging에도 같은 `<commit-sha-short>`를 쓴다.
