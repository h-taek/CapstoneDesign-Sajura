# MVP 범위 정의서

## 1. MVP 목표

- 핵심 흐름(데이터 업로드 → 예측 → 발주 추천 → 점주 승인 → 쿠팡 자동화)을 실제 동작 수준으로 완성한다.
- 1차 검증 업종(주점) 데이터로 모델을 학습하고 예측 정확도를 검증한다.
- 프로토타입과 MVP가 동일한 아키텍처를 공유하여 단계적으로 확장한다.

---

## 2. 1차 검증 업종

**주점**

- 보유한 주점 POS 데이터를 기반으로 모델 학습 및 예측을 수행한다.
- 단일 업종 집중으로 초기 모델 검증의 정확도를 높인다.
- 이후 카페·치킨집 등 다른 업종으로 확장한다.

**데이터 소스:** 보유 중인 주점 POS 데이터 → CSV 업로드로 적재

## 4. MVP 제외 기능 (1차 유예)

| 기능 | 제외 이유 | 추가 단계 |

## 7. MVP 성공 기준

### 기능 완성 기준

데모 시나리오 Step 1~6이 오류 없이 end-to-end로 동작해야 한다.

| 항목 | 기준 |
|------|------|
| 수요예측 결과 표시 | 메뉴별 1~3일 예측값 + 신뢰도 배지 화면 정상 표시 |
| 예측 근거 표시 | 산출 방법·출력 형태 확정 시점에 정상 표시 (research §3) |
| 추천발주 이력 기록 | 점주 수정·승인 후 `order_approval_logs`에 이력 저장 확인 |
| 쿠팡 자동화 | 성공·부분 실패·전체 실패 분기 모두 화면 정상 처리 |
| n8n 배치 | 수동 트리거 시 `pipeline_jobs` 상태가 DONE으로 전환 |

### 예측 품질 기준

- MVP 단계 예측 품질 평가 지표 선정 및 정량 목표는 AI probe 후 확정한다.
- 초기 모델은 "신뢰도 낮음" 배지가 붙을 수 있음을 인정하고 시작한다. 모델 고도화는 2단계에서 수행한다.

### 성능 기준

> performance.md 섹션 1.1 기준 (MVP 50개 매장·20명 동시 접속 기준)

| 항목 | 기준 |
|------|------|
| 일반 API 응답 | 200ms 이하 |
| 예측 결과 조회 (캐시 hit) | 300ms 이하 |
| 시연 환경 매장 수 | 최소 1~5개 매장 정상 동작 확인 |

## 6. 데모 시나리오

**시나리오: 신규 점주 온보딩 → 당일 발주까지**

| Step | 행위 | 확인 포인트 |
|------|------|------------|
| 1. 로그인 및 온보딩 | 소셜 로그인 → 사업자번호 검증 → 매장 정보 입력 → CSV 임시 모드 선택 | 국세청 API 검증 결과, onboarding_completed 전환 |
| 2. 데이터 적재 | 주점 POS 데이터 CSV 업로드 → 메뉴·레시피 등록 → 초기 재고 입력 | 업로드 파싱 성공 건수, 이상치 감지 결과 |
| 3. 배치 실행 | n8n 워크플로우 수동 트리거 → AI Server 예측·추천발주 생성 → DB 저장 | pipeline_jobs 상태 DONE 전환, forecast_results 생성 확인 |
| 4. 수요예측 확인 | 메뉴별 1~3일 예상 수요 조회 → 예측 근거 확인 → 신뢰도 배지 확인 | 예측 근거 표시(형태는 research §3), 신뢰도 낮음 배지 동작 |
| 5. 추천발주 승인 | 품목별 권장 수량·예상 소진 시점 확인 → 수량 수정 → 발주 확정 | 수정 이력 저장 (order_approval_logs), 발주 확정 처리 |
| 6. 쿠팡 자동화 | Playwright가 쿠팡 장바구니에 품목 자동 담기 → 결과 화면 표시 | 성공 품목·실패 품목 분리 표시, 수동 처리 안내 |

## 8. 데이터 확보 방식

**현황:** POS 연동 API 없이 보유 중인 주점 POS 데이터를 사용한다.

| 항목 | 내용 |
|------|------|
| 데이터 소스 | 팀 보유 주점 POS 데이터 (실제 매장 판매 이력) |
| 적재 방식 | CSV 파일 변환 후 `POST /api/sales/upload` 로 업로드 |
| 전처리 | 업로드 시 파싱·이상치 감지 자동 수행, 파싱 실패 건수 화면에 표시 |
| 기대 기간 | 수요예측 학습에 필요한 최소 30일 이상 데이터 확보 목표 |
| 한계 | 단일 매장 데이터이므로 초기 모델은 "신뢰도 낮음" 배지가 붙을 수 있음 |

> 학습 데이터 기간·예측 오차 임계 조건은 AI probe 후 확정. 초기 모델에는 신뢰도 낮음 배지가 자주 표시될 수 있음.

## 9. 개발 역할 분담

> 세부 일정은 별도 간트차트로 관리한다.

| 파트 | 담당 업무 | 팀원 |
|------|----------|------|
| Frontend | 화면 설계, React 개발, PWA 기술 적용, 수요예측·재고·발주 UI | 정동욱, 이민욱, 임형택 |
| AI Modeling | 데이터 수집·전처리, 모델 학습·평가, 예측 근거 구현(산출 방법·출력 형태는 research §3), n8n AI 파이프라인 연동 | 정동욱, 이민욱, 서창현 |
| Backend | REST API 서버, DB 설계·운영, n8n 배치 파이프라인, 쿠팡 자동화 | 서창현, 임형택 |

**파트 간 공유 책임:**
- n8n 파이프라인 설계: Backend 주도, AI Modeling 연동 협의
- 데모 시나리오 검증: 전 파트 참여 (Step 1~6 end-to-end 검증)
