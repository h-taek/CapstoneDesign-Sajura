# 사용자 흐름 설계서

## 1. 주요 사용자

- 오프라인 식음료 매장 운영자
- 음식점 및 카페 소상공인
- 식자재 재고 관리에 어려움을 겪는 자영업자
- 데이터 기반 경영을 원하지만 IT 역량이 부족한 사용자

---

## 2. 핵심 사용 흐름

```text
[공통 시작]
회원가입(이메일)/로그인/소셜 로그인
→ business_status 확인
    ├─ UNVERIFIED·REJECTED → 사업자 검증 화면
    └─ PENDING·VERIFIED → onboarding_completed 확인
                ├─ false → 온보딩 흐름 시작
                └─ true  → 메인 홈

[사업자 검증 (온보딩과 분리된 게이트, NTS 자동 + 관리자 승인 병행)]
사업자등록번호 + 사업자등록증 업로드
→ ① 국세청 API 검증 (마스터 코드면 곧바로 VERIFIED)
    ├─ 미등록/형식 → 재입력 (상태 유지)
    ├─ 휴업/폐업 → 진행 불가, 사유 안내 (상태 유지)
    └─ 계속사업자 → ② 등록증 업로드 → business_status=PENDING → 온보딩 흐름 시작
                      └─ 관리자 심사: 승인 → VERIFIED / 반려 → REJECTED(사유) → 재검증

[관리자 심사 흐름 (role=ADMIN)]
/admin 심사 큐 → PENDING 목록·등록증 확인 → 승인(VERIFIED) 또는 반려(사유 입력→REJECTED)

[온보딩 흐름]
매장 정보 입력
→ POS 연동 시도 [POS API는 2단계 — MVP는 CSV 모드 기본]
    ├─ POS API 성공 [2단계] → 초기 재고/메뉴 입력 → 메인 홈
    └─ CSV 모드 (MVP 기본 경로) → CSV 업로드 → 초기 재고/메뉴 입력 → 메인 홈
                                (양쪽 모두 수요예측·자동발주 활성화)

[일일 운영 흐름]
메인 홈 접속
→ 수요예측 확인
→ 추천발주 확인
→ 점주 수정/승인
→ 쿠팡 장바구니 자동 담기 시도
    ├─ 전체 성공 → 쿠팡에서 결제 진행
    ├─ 부분 실패 → 성공 품목 담기 완료 + 실패 품목 수동 처리 안내
    └─ 전체 실패 → 전체 품목 수동 처리 안내
```

---

## 3. 온보딩 흐름

> 온보딩 입력 항목 및 POS 상태 기준: feature_spec.md 섹션 1.4

1. 사용자가 이메일 회원가입 또는 Google/카카오 로그인으로 계정을 만든다. (Authlib OAuth 2.0, Firebase 미사용) → `business_status=UNVERIFIED`
2. 인증 완료 후 `business_status`·`onboarding_completed`를 확인한다. `UNVERIFIED`·`REJECTED`면 사업자 검증 화면으로 이동한다.
3. (검증 게이트, 온보딩과 분리) 사업자등록번호를 입력하면 국세청 API로 즉시 검증한다.
   - 미등록 / 형식 오류 → 재입력 (상태 유지)
   - 휴업 / 폐업 → 진행 불가, 사유 안내 (상태 유지)
   - 계속사업자(또는 마스터 코드) → **사업자등록증 업로드** → `business_status=PENDING` → 온보딩 진행 (관리자 승인 전이라도 진입 가능, 1-B)
   - 관리자 심사: 승인 → `VERIFIED` / 반려 → `REJECTED`(사유) → 재검증
4. 매장명, 업종, 연락처, 주소, 매장 규모 구간, 운영 형태를 입력한다.
5. POS 연동 방식을 선택한다.
   - **CSV 모드 (MVP 기본 경로)** → CSV 템플릿 다운로드 → 보유 POS 데이터 업로드
   - **POS API 연동 [2단계]** → POS 종류·자격증명 입력 → 연동 시도
     - 성공: `pos_mode=api`, "POS 연동 완료" 배지
     - 실패: CSV 모드로 진행 (`pos_mode=csv`)
   - 양쪽 모두 수요예측·자동발주 추천 활성화
   - 설정 화면에서 모드 전환 가능
6. 초기 재고와 초기 메뉴를 입력한다.
7. 메인 홈 화면으로 이동한다.

중도 이탈 후 재접속 시 마지막 스텝부터 재진입하며, 기존 입력 데이터는 유지된다.

---

## 4. 일일 운영 흐름

1. 점주가 메인 홈에 접속한다.
2. 시스템이 저장된 예측 결과와 추천발주안을 조회한다.
3. 점주가 메뉴별 예상 수요를 확인한다.
4. 점주가 품목별 권장 발주 수량과 예상 소진 시점을 확인한다.
5. 점주가 추천 근거와 예측 신뢰도를 확인한다.
6. 점주가 발주 수량 또는 상품을 수정할 수 있다.
7. 점주가 발주를 확정한다.
8. 시스템이 쿠팡 장바구니 자동 담기를 시도한다.
9. 결과에 따라 분기한다. (상세: 섹션 13)

---

## 5. 재고 관리 흐름

1. 점주가 재고 관리 화면에 진입한다.
2. 재고 목록을 확인한다. (기본 정렬: 소비기한 임박순)
3. 신규 입고 시 새 로트를 추가한다 (재료명, 수량, 단위, 소비기한, 단가).
4. 기존 로트의 수량 또는 소비기한을 직접 수정할 수 있다. 수정 사유를 필수 입력한다.
5. 폐기할 식자재가 있으면 폐기 요청을 입력한다.
6. 시스템이 폐기 가능 수량을 검증한다.
   - 폐기 가능 → 재고를 차감한다.
   - 폐기 불가 → 오류를 표시한다.

---

## 6. 메뉴 관리 흐름

1. 점주가 메뉴 관리 화면에 진입한다.
2. 메뉴 목록을 확인한다.
3. 메뉴를 등록, 수정, 삭제한다.
4. 메뉴 등록 시 메뉴명 중복을 확인한다.
5. 레시피가 있으면 메뉴와 함께 저장한다.
6. 재고 차감 ON + 레시피 미입력 시 경고 메시지를 수신한다.
7. 삭제는 소프트 삭제로 처리된다. 과거 판매 데이터는 유지된다.

---

## 7. 판매 데이터 조회 흐름

1. 점주가 판매 데이터 화면에 진입한다.
2. 조회 기간을 선택한다. (최대 1년 범위)
3. 판매 목록을 확인한다. (기본 정렬: 날짜 최신순)
4. 특정 날짜 또는 판매 항목을 선택해 시간대별 판매 내역과 메뉴별 판매 수량 상세를 확인한다.

---

## 8. 사용자 통제 흐름

- AI는 추천만 수행한다.
- 점주는 발주 전 추천안을 확인한다.
- 점주는 추천안을 수정할 수 있다.
- 최종 발주 확정은 점주의 명시적 승인으로 수행한다.
- 자동 발주 추천은 자동 결제가 아니다.

---

## 9. 화면 IA

```text
/ (루트)
├── 로그인 / 이메일 회원가입
├── 온보딩  ← onboarding_completed: false 시 강제 진입
│   ├── Step 1: 사업자 인증  ← 온보딩과 분리된 검증 게이트 (/verify-business, business_status: UNVERIFIED·REJECTED 시 강제 진입)
│   ├── Step 2: 매장 정보 입력
│   ├── Step 3: POS 연동
│   └── Step 4: 초기 재고/메뉴 입력
├── 관리자 심사 (/admin)  ← role=ADMIN 전용, 심사 큐·승인/반려 (feature_spec §12.11)
└── 메인  ← 온보딩 완료 후 접근 가능
    ├── 홈
    │   └── 알림 목록 (인앱)
    ├── 대시보드
    ├── 재고 관리
    │   └── 재료 상세
    │       └── 로트 목록 (수정 / 폐기)
    ├── 메뉴 관리
    │   └── 메뉴 등록 / 수정 / 상세
    ├── 판매 데이터
    │   └── 판매 상세
    ├── 수요예측
    ├── 추천발주
    │   ├── 최종 발주 확인
    │   └── 담기 결과 (성공 품목 / 실패 품목)
    └── 설정
        ├── POS 연동 관리
        ├── 단가 관리
        ├── 알림 설정
        ├── 계정 정보
        └── 앱 정보
```

하단 네비게이션 바 (5개 탭 고정): 홈 / 재고 / 예측 / 발주 / 설정

## 10. 대시보드/ROI 조회 흐름

> 지표 산식 기준: feature_spec.md 섹션 8.2

1. 점주가 대시보드 화면에 진입한다.
2. 기본 조회 기간(주별)의 데이터가 자동으로 표시된다.
3. 조회 기간을 변경하며 아래 지표를 확인한다.
   - 기간별 매출 추이 (선 그래프)
   - 메뉴별 판매 비중 (도넛 차트)
   - 수요예측 vs 실제 판매량 비교 (선 그래프)
   - 폐기율 추세 / 예측 정확도 지표 추세 (선 그래프)
   - 월별 폐기 비용 / 전월 대비 폐기 비용 변화율 (막대 그래프 + 수치)

## 11. 소비기한 관리 흐름

> 소비기한 알림 기준: feature_spec.md 섹션 3.6

1. 야간 배치(02:00)에서 전체 로트의 소비기한을 자동 체크한다.
2. 조건에 따라 분기한다.
   - D-3일 임박: 경고 알림 발송 + 재고 목록에 경고 배지 표시
   - D-1일 임박: 긴급 알림 발송 + 재고 목록에 긴급 배지 표시
   - 소비기한 초과: 폐기 요청 알림 발송 (자동 폐기 없음)
3. 점주가 알림을 확인하고 재고 관리 화면으로 이동한다.
4. 해당 로트를 선택하고 폐기 처리를 수행한다.
   - 폐기 가능 수량 충족 → 재고 차감
   - 수량 부족 → 오류 표시

---

## 12. 알림 수신 흐름

> 알림 채널 및 긴급도 기준: feature_spec.md 섹션 11

알림 채널: 점주 대상 → 앱 내 알림(푸시 + 인앱), 파이프라인 실패 → 개발팀 Slack

1. 알림 발생 시 점주의 앱으로 푸시 알림이 발송된다.
2. 앱 접속 시 홈 화면의 경고 배지 영역에 활성 알림이 우선순위 순으로 표시된다.
   - 우선순위: 긴급 → 경고 → 정보
3. 알림 항목을 탭하면 해당 기능 화면으로 이동한다.

| 알림 상황 | 이동 화면 |
|----------|----------|
| 재고 부족 ("재고 확인 필요") | 재고 관리 |
| 소비기한 D-3 / D-1 임박 | 재고 상세 |
| 소비기한 초과 폐기 요청 | 재고 상세 |
| 이상치 감지(임계 조건은 research 확정) | 판매 데이터 |
| 예측 완료 + 추천발주안 생성 | 추천발주 |

4. 설정 > 알림 설정에서 알림 유형별 on/off를 변경할 수 있다.

---

## 13. 쿠팡 자동화 실패 분기 흐름

> 실패 처리 정책 기준: feature_spec.md 섹션 7.2

1. 점주가 발주를 확정하면 Playwright가 쿠팡 장바구니 자동 담기를 시도한다.
2. 결과에 따라 분기한다. (재시도 없음 — 실패 즉시 수동 처리 안내)

| 결과 | 처리 |
|------|------|
| 전체 성공 | 쿠팡 결제 진행 안내 화면 표시 |
| 부분 실패 | 성공 품목 담기 완료 + 실패 품목 목록 + 수동 처리 안내 |
| 전체 실패 | 전체 품목 목록 + 수동 처리 안내 |

3. 점주가 쿠팡 앱/웹에서 실패 품목을 직접 처리한다.

---

## 14. 리드타임/안전재고 설정 흐름

> 기본값 및 DEFAULT_USED 상태 기준: feature_spec.md 섹션 6.1

1. 점주가 재고 관리 화면에서 재료를 선택한다.
2. 재료 상세 화면에서 리드타임(일 단위)과 안전재고를 입력하고 저장한다.
3. 저장된 값은 다음 추천발주 생성 시 반영된다.
4. 미설정 재료는 시스템 기본값(리드타임 1일, 안전재고 0)을 사용하며 `DEFAULT_USED` 상태로 설정 필요 안내를 표시한다.

---

## 15. 설정 관리 흐름

1. 점주가 하단 네비게이션 바 > 설정 화면에 진입한다.
2. 항목별 흐름:

| 항목 | 흐름 |
|------|------|
| POS 연동 관리 | 현재 연동 상태 확인 → POS 재연동 시도 또는 CSV 업로드 선택 |
| 단가 관리 | 재료별 단가 및 최종 업데이트 일시 확인 → 수동 단가 수정 |
| 알림 설정 | 알림 유형별 on/off 토글 (소비기한 임박 / 재고 부족 / 예측 완료 / 이상치 감지) |
| 계정 정보 | 매장 정보 수정 / 로그아웃 / 회원 탈퇴 (탈퇴 후 30일 뒤 데이터 영구 삭제) |
| 앱 정보 | 앱 버전, 이용약관, 개인정보처리방침 확인 |
