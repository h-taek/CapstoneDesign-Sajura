## 2. 인증 통합

> 토큰 정책: `03_be.md` §7.3 / OAuth API: `02_implementation_design.md` §3.2

| 항목 | 결정 |
|------|------|
| OAuth 흐름 | BE 리다이렉트 방식 — FE는 BE 인가 URL(`/api/auth/login/{provider}`)로 이동만 하고, BE 콜백에서 JWT 발급 후 FE root("/")로 302 redirect |

| 첫 진입 시 동기 | FE 마운트 시 메모리 Access Token 부재 감지 → `POST /api/auth/refresh` 1회 호출로 Access Token 동기 |

| 로그아웃 | `POST /api/auth/logout` 호출 후 메모리 스토어 클리어 + root로 이동 |

## 3. 라우팅 구조

> 화면 구성: §4 / 사용 흐름: `01_basic_design.md` §4

| 경로 | 화면 | 가드 |
|------|------|------|
| `/login` | 로그인 (이메일/비밀번호 + Google·카카오 버튼) | 미인증만 |
| `/register` | 이메일 회원가입 (email·password·name) | 미인증만 |
| `/intro` | 서비스 소개(랜딩) — 기능·이용 방법·앱(PWA) 설치·FAQ, 가입/로그인 진입 | 없음 (누구나) |
| `/verify-business` | 사업자 검증 (사업자번호 입력 + 등록증 업로드, 반려 사유 표시) | 인증 + `business_status` ∈ {UNVERIFIED, REJECTED} |
| `/onboarding/*` | 온보딩 (매장 정보·POS 연동·초기 재고/메뉴) | 인증 + `business_status` ∈ {PENDING, VERIFIED} + `onboarding_completed=false` |
| `/` | 홈 (오늘의 요약 + 경고 배지) | 인증 + 온보딩 완료 |
| `/dashboard` | 대시보드 (매출·예측) | 인증 + 온보딩 완료 |
| `/inventory` | 재고 관리 (목록·상세) | 동상 |
| `/menus` | 메뉴 관리 | 동상 |
| `/sales` | 판매 데이터 조회 | 동상 |
| `/forecast` | 수요예측 (1·2·3일 탭) | 동상 |
| `/orders` | 추천발주·승인 | 동상 |
| `/orders/{id}/result` | 쿠팡 자동화 결과 (사주라 확장 연동 — §12) | 동상 |
| `/settings/*` | 설정 (POS·알림·계정·앱 정보) | 동상 |
| `/admin/verifications` | (관리자) 사업자 검증 심사 큐 — 등록증 확인·승인/반려 | 인증 + `role=ADMIN` |

- 가드 미통과 시 redirect 순서: 미인증 → `/login` / `business_status` ∈ {UNVERIFIED, REJECTED} → `/verify-business` / {PENDING, VERIFIED} && 온보딩 미완료 → `/onboarding/{현재 스텝}` / 모두 완료 → `/`. `role=ADMIN`이 아닌데 `/admin/*` 접근 시 → `/`.
- MVP 제외 기능(`02_implementation_design.md` §1.4)의 화면은 노출하지 않거나 '준비 중' 화면으로 대신하고, 라우트를 미리 등록하지 않는다.
- 라우터는 React Router v7 data router 모드(loader/action)를 사용하되, 서버 데이터는 TanStack Query에 위임한다(loader는 권한 가드·라우트 진입 조건 검증 위주).

## 4. 화면 구성

### 4.0 화면 IA

```text
/ (루트)
├── 로그인 / 이메일 회원가입
├── 온보딩  ← onboarding_completed: false 시 강제 진입
│   ├── Step 1: 사업자 인증  ← 온보딩과 분리된 검증 게이트 (§4.2)
│   ├── Step 2: 매장 정보 입력
│   ├── Step 3: POS 연동
│   └── Step 4: 초기 재고/메뉴 입력
├── 관리자 심사 (/admin/verifications)  ← role=ADMIN 전용 (§4.11)
└── 메인  ← 온보딩 완료 후 접근 가능
    ├── 홈
    │   └── 알림 목록 (인앱)
    ├── 대시보드
    ├── 재고 관리
    │   └── 재료 펼침 (입고 대기 발주 / 입고 / 로트 수정·폐기)
    ├── 메뉴 관리
    │   └── 메뉴 편집 (판매가 + 레시피) / 메뉴 추가
    ├── 판매 데이터
    │   └── 판매 상세
    ├── 수요예측
    ├── 추천발주
    │   ├── 최종 발주 확인
    │   └── 담기 결과 (성공 품목 / 실패 품목)
    └── 설정
        ├── POS 연동 관리
        ├── 알림 설정
        ├── 계정 정보
        └── 앱 정보
```

하단 네비게이션 바 (5개 탭 고정): 홈 / 재고 / 예측 / 발주 / 설정

### 4.2 온보딩

- 상단에 진행 단계 표시 (1/4, 2/4...)
- Step 4 완료 전까지 메인 화면 진입 불가
- 입력 도중 앱 종료 시 다음 접속에서 해당 스텝부터 재진입, 기존 입력 데이터 유지
- Step 1(사업자 인증)은 온보딩과 분리된 검증 게이트다. 별도 라우트 `/verify-business`(§3)이며, `business_status` ∈ {UNVERIFIED, REJECTED}일 때 강제 진입한다. 진행 단계 표시상으로만 Step 1로 노출한다. 검증 흐름: `01_basic_design.md` §3.1.4 / §4.2

| 스텝 | 구성 요소 |
|---|---|
| Step 1. 사업자 인증 (`/verify-business`) | 사업자등록번호 입력 필드, 인증 요청 버튼, 인증 결과 메시지, 사업자등록증 업로드 영역(계속사업자 확인 후 노출), 심사 대기(PENDING) 안내, 반려(REJECTED) 시 반려 사유 표시 + 재검증 진입 |
| Step 2. 매장 정보 입력 | 매장명 / 업종 / 연락처 / 주소 입력 필드, 매장 규모 구간 선택, 운영 형태 선택 |
| Step 3. POS 연동 | 연동 방식 선택. CSV 템플릿 다운로드·업로드는 설정 > POS 연동 관리(§4.10)에서 한다 (`01_basic_design.md` §3.4.4). 모드 선택 (CSV / POS API), POS 종류 선택(토스플레이스·키움페이·OKPOS)·자격증명 입력 필드, 연동 결과 메시지 (`01_basic_design.md` §3.4.3) |
| Step 4. 초기 재고/메뉴 입력 | 재고 추가 폼 (재료명/수량/단위/소비기한/구매 금액), 메뉴 추가 폼 (메뉴명/가격 — 재고 차감 OFF로 등록, 레시피는 이후 메뉴 관리에서), 완료 버튼 |

### 4.5 메뉴 관리

- 메뉴 판매가와 레시피를 한 화면에서 받는다. 판매가 수정 화면을 따로 두지 않는다
- 레시피 재료는 등록된 재고 목록에서 고른다

| 구성 요소 | 설명 |
|---|---|
| 메뉴 목록 | 메뉴명, 판매가. 고른 메뉴를 강조 |
| 메뉴 추가 버튼 | 빈 편집 화면을 연다 |
| 편집 화면 | 메뉴명, 판매가, 카테고리(선택), 레시피(재료 + 사용량 + 단위). 저장 한 번에 메뉴와 레시피를 함께 저장 |
| 재고 차감 토글 | 레시피가 저장된 메뉴만 켤 수 있음. 누르면 바로 반영 |
| 메뉴 삭제 | 확인 후 삭제 |

### 4.6 재고 관리

- 재고 목록은 FE가 정렬한다. 기준: 소비기한(기본) / 재료명 / 총 수량 각각 오름·내림차순(웹 머리글), 앱 정렬 선택에는 경고 우선도 있다. 소비기한 없는 재료는 방향과 무관하게 맨 뒤. 고른 정렬은 preferences 스토어에 저장
- 경고는 배지 없이 해당 글씨를 `text-danger`로 표시한다. FE가 품목 값으로 판정한다

| 경고 | 조건 | 빨갛게 하는 글씨 |
|---|---|---|
| 소비기한 | `nearest_expiry_date` ≤ 오늘 + 3일 (지난 것 포함) | 소비기한 |
| 수량 | `needs_check` 또는 `total_quantity` ≤ `low_stock_threshold` (0 포함) | 총 수량 |

- '확인 필요' 보기는 두 경고 중 하나라도 해당하는 재료만 보여준다
- 폐기 처리는 로트별로 수행

| 구성 요소 | 설명 |
|---|---|
| 재료 목록 | 재료명, 총 수량, 가장 이른 소비기한(D-n), 재주문 임계값, 안전재고 |
| 재료 추가 버튼 | 등록 폼 열기 |
| 재료 펼침 | 맨 위에 입고 대기 카드(§4.6.1), 신규 입고 폼, 로트 목록(입고일, 소비기한, 입고 수량, 잔여 수량, 구매 금액), 로트별 수정/폐기 |
| 쿠팡 상품 줄 | 재료 펼침 안. 연결된 쿠팡 상품명·판매가·단가. 연결은 있는데 단가가 미설정이면 포장 수량 입력칸(`PATCH /api/inventory/{item_id}`의 `pack_quantity`, `01_basic_design.md` §3.3.1) |
| 재료 추가 폼 | 재료명, 수량, 단위, 소비기한, 구매 금액, 재주문 임계값, 안전재고, 리드타임 |

#### 4.6.1 입고 대기 카드

- `GET /api/inventory/{item_id}/lots`의 `pending_orders`를 확정일 오래된 순으로 카드 하나씩 보여준다 (`01_basic_design.md` §3.7.5)
- 카드 제목: '○월 ○일 확정 발주 · 확정 수량 · 확정 금액(있을 때)'
- 입력 기본값: 입고 수량 = 확정 수량, 입고일 = 오늘, 소비기한 = 빈칸, 구매 금액 = 확정 소계(없으면 빈칸)
- 버튼: 입고 처리(`POST /api/orders/items/{id}/receive`), 입고 안 함(`POST /api/orders/items/{id}/skip`)

### 4.7 판매 데이터

- 판매 목록에서 날짜를 선택하면 그날의 판매 상세로 이동

| 구성 요소 | 설명 |
|---|---|
| 기간 선택기 | 시작일 ~ 종료일, 최대 1년 |
| 판매 목록 | 날짜, 메뉴명, 판매 수량, 매출액 (날짜 최신순) |
| 기간 합계 | 총 판매 건수, 총 매출액 |
| 판매 상세 | 그날의 시간대별 판매 내역(시각순), 메뉴별 판매 수량, 그날 총 매출액 |

### 4.8 수요예측

- 1일/2일/3일 탭 구성
- 메뉴 기본 정렬: 예측 판매량 높은 순

| 구성 요소 | 설명 |
|---|---|
| 일자 탭 | 1일 후 / 2일 후 / 3일 후 |
| 메뉴별 예측 카드 | 메뉴명, 예상 판매량, 신뢰도 낮음 경고 배지 |
| 예측 근거 (펼치기) | top-3 기여 요인 + 자연어 1문장 (`05_ai.md` §8) |
| 신뢰도 경고 상세 | 배지 탭 시 `low_confidence_reason` 코드별 경고 사유 표시 (`01_basic_design.md` §3.6.3) |

### 4.9 추천발주

- 품목 기본 정렬: 재료명 가나다순
- 품목별 체크박스로 부분 선택 후 승인 가능
- 저장된 예측이 없어 추천안을 받지 못하면(`FORECAST_NOT_FOUND`) 대체 추천 없이 수동 실행(`POST /api/forecast/run`)을 안내. 실행 실패(`AI_INSUFFICIENT_HISTORY`, `PIPELINE_AI_SERVER_UNAVAILABLE`)는 사유만 표시
- 단가는 서버 값만 보여준다. 화면에서 단가를 고치지 않는다 (`01_basic_design.md` §3.3.1)
- 확정이 끝나거나 409(이미 확정한 추천안)를 받으면 추천을 새로 받는다

## 7. API 통합

### 7.0 책임 경계

BE는 값을 가공 없이 전달하고, 화면 표시를 위한 판단(정렬, 경고 배지, D-n, 개수 세기)은 FE가 한다. 기준값은 spec 한 곳을 따른다 (`03_be.md` §2).

### 7.1 OpenAPI 코드젠

- `scripts/export_openapi.py`가 서버 없이 FastAPI 앱에서 명세를 뽑아 `Front/openapi.json`으로 저장한다. 이 파일은 저장소에 커밋한다.
- `pnpm gen:api`가 `openapi-typescript`로 `src/api/types.gen.ts`를 생성한다. 기본값이 있는 필드는 선택(`--default-non-nullable false`)으로 둔다. 응답에 항상 담기는 기본값 필드는 BE 스키마에 `json_schema_serialization_defaults_required`로 필수 표시한다.
- `src/api/endpoints/*`의 요청·응답 타입은 생성 타입의 별칭(`components["schemas"][...]`)으로 정의한다. BE 스키마가 아닌 클라이언트 전용 값(파일 blob, 폼 옵션)만 직접 선언한다.
- BE API 변경 시 FE CI 단계에서 type 검사로 즉시 감지된다.

### 7.2 ky 인스턴스 정책

| 항목 | 값 |
|------|----|
| baseUrl | 환경변수 `VITE_API_BASE_URL` |
| credentials | `'include'` (HttpOnly Refresh Cookie 동봉) |
| Access Token 부착 | request hook에서 메모리 스토어 토큰 read |
| 401 처리 | response hook에서 `POST /api/auth/refresh` 1회 시도 → 성공 시 원 요청 재시도, 실패 시 로그아웃 |
| 재시도 | 5xx만 1회 (멱등 동사에 한정) |
| 타임아웃 | 10초 |

## 12. 브라우저 확장

> 쿠팡 장바구니 자동 담기를 담당한다. 기능 규칙: `01_basic_design.md` §3.8 / API 계약: `02_implementation_design.md` §3.7

### 12.1 목적과 산출물

- 발주 확정 품목을 점주의 쿠팡 장바구니에 자동으로 담는다.
- 사주라 서버는 쿠팡 자격증명을 수집·저장하지 않는다.
- 산출물은 PWA와 별개 배포 단위인 Chrome 확장(Manifest V3)이다.

| 항목 | 결정 |
|---|---|
| 이름 | 사주라 확장 (Sajura Extension) |
| 플랫폼 | Chrome Manifest V3 |
| 배포 단위 | PWA와 분리. 저장소 디렉터리도 분리한다 |

### 12.2 권한 범위

| 항목 | 값 |
|---|---|
| `host_permissions` | `*://*.coupang.com/*` 만 |
| `externally_connectable.matches` | 사주라 PWA 도메인만 |
| 그 외 | `<all_urls>`·`tabs` 전체 권한·쿠키 접근을 요청하지 않는다 |

`window.postMessage` 릴레이 대신 `externally_connectable`을 쓴다. 사주라 도메인에 content script를 주입하지 않는다.

### 12.3 실행 흐름

확장은 서버의 LLM이 쿠팡 화면을 보고 정한 동작을 한 걸음씩 실행하는 에이전트다.

```text
[PWA]  점주가 발주 확정 → [담기] → 품목·수량을 확장에 넘긴다 (externally_connectable)
[확장]  쿠팡 탭을 열고 품목마다 반복:
          서버 LLM이 화면 보기·동작을 요청 → 확장이 실행하고 결과를 돌려준다 → 담길 때까지 반복
[확장]  품목별 결과(담은 상품·가격·단위가격 / 실패)를 PWA로
[PWA]  POST /api/orders/{order_id}/automate/result → 공용 쿠팡 상품·재료 연결·orders.status 갱신
[PWA]  결과 화면(성공/실패 품목). 결제는 점주가 쿠팡에서 직접 한다
```

- 확장이 먼저 화면을 보내지 않는다. LLM이 요청한 보기·동작만 실행한다(§12.4).
- 모든 품목이 끝나면 장바구니 검수 대화를 한 번 연다. LLM은 장바구니 화면에서 품목별로 담으려던 상품·수량과 맞는지 보고, 모자라면 장바구니에서 수량을 늘린다. 많으면 줄이지 않고 그 품목을 '확인 필요'로 남긴다. 점주가 원래 담아 둔 같은 상품과 합쳐졌을 수 있기 때문이다. 담기를 시작하기 전의 장바구니는 읽지 않는다.
- 대화는 품목마다 새로 시작한다. 대화 기록에는 가장 최근 요소 목록만 남긴다(`03_be.md` §2.4.1).
- 반복은 PWA가 주도한다. PWA가 로그인 토큰으로 서버에 다음 요청을 묻고, 받은 요청을 확장에 넘기고, 확장의 실행 결과를 서버에 보낸다. 확장은 서버를 직접 부르지 않는다. 담기가 끝날 때까지 사주라 탭이 열려 있어야 한다.
- LLM은 도구 호출로만 답하고, 품목 끝 도구로 그 품목을 마친다(`03_be.md` §2.4.4).
- LLM API 키는 서버 환경변수로만 두고 Frontend·확장에 노출하지 않는다.
- 오남용 방지 규칙과 보안 분류기: `03_be.md` §2.4.2·§2.4.3. 담기 속도를 제한하는 상한은 두지 않는다.

### 12.4 화면 보기와 동작

LLM이 요청할 수 있는 것은 아래뿐이다. 캡처와 좌표는 쓰지 않는다.

| 구분 | 요청 | 확장의 처리 |
|---|---|---|
| 보기 | 요소 목록 | 지금 쿠팡 화면의 요소 목록을 만들어 개인정보를 가린 뒤 돌려준다 |
| 동작 | 클릭(요소 번호) | 그 요소를 스크립트로 누른다. 링크면 새 탭 속성(`target`)을 지우고 눌러 같은 탭에서 연다 |
| | 입력(요소 번호, 글자) | 그 입력칸에 글자를 넣는다 |
| | 스크롤 | 화면을 내리거나 올린다 |

- 확장은 담기를 시작할 때 연 작업 탭 하나에서만 동작한다. 점주가 연 다른 쿠팡 탭은 건드리지 않는다.
- 클릭·입력 뒤 화면이 바뀌면 다 뜰 때까지 기다리고, 결과에 화면이 바뀌었음을 알린다. 요소 번호는 그 화면에서만 유효하다. 없는 번호면 '요소 없음'을 돌려준다.
- 검색은 검색창에 입력한 뒤 검색 버튼을 클릭한다. 스크립트 엔터로는 검색되지 않는다.
- 담을 개수는 LLM이 정한다. 수량은 상품 페이지의 수량 버튼 클릭으로 맞춘다. 수량 칸에 스크립트로 넣은 값은 담기에 반영되지 않는다. 쿠팡 수량 버튼 이름이 실제 동작과 반대이므로(`research/backend/16_coupang_page_probe.md` §6.4) 담긴 수량은 마지막 장바구니 검수에서 확인한다.

요소 목록은 화면 전체(보이지 않는 부분 포함)를 담는다. 쿠팡용으로 확장이 직접 만들고, 요소마다 번호·종류·글자를 붙이며 아래를 포함한다.

- 상품 카드의 글자: 상품명, 취소선 가격, 할인율, 표시 가격, 단위가격 표시, 별점, 리뷰 수, 광고 표시
- 글자 없는 그림 배지는 그림 파일 이름 (예: 로켓프레시 `logo_fresh_medium.png`)
- 버튼·링크로 표시되지 않았지만 누를 수 있는 글자 (예: 장바구니 상품별 '삭제')

개인정보는 요소 목록을 돌려주기 전에 값을 `---`로 바꾼다. 요소는 남긴다.

| 대상 | 찾는 방법 |
|---|---|
| 회원 이름 | 위치 — 머리말의 이름 표시와 '마이쿠팡' 링크의 설명 글('<이름>님 마이쿠팡 바로가기') |
| 전화번호·이메일·주소 | 모양 — 화면 어디에서든 전화번호·이메일·주소 형태의 글자 |

- 이름은 '○○님' 모양으로 찾지 않는다.
- 근거 실측: `research/backend/16_coupang_page_probe.md` §6.

### 12.5 담기 결과로 보내는 데이터

품목별 결과는 아래 필드로 한정한다. 요청 형식: `02_implementation_design.md` §3.7.

| 필드 | 내용 |
|---|---|
| `product_id`·`vendor_item_id` | 쿠팡 상품 고유 ID |
| `product_name` | 상품명 |
| `display_price` | 표시 가격(원) |
| `discount_label` | 할인 표시 글자 원문 (예: '할인'·'쿠폰할인'·'와우쿠폰할인'). 없으면 null |
| `unit_price_text` | 쿠팡 단위가격 표시 원문 (예: '100g당 2,348원'). 없으면 null |
| `rocket_fresh` | 로켓프레시 상품 여부 |

### 12.6 로그인 상태

확장은 담기를 시작하기 전에 쿠팡 로그인 여부를 확인한다. 로그인을 요구하지는 않는다.

- 비로그인이면 '로그인하지 않으면 로켓프레시 상품은 담을 수 없습니다' 알림을 띄우고 담기를 계속한다.
- 비로그인이면 로켓프레시 상품을 선택 대상에서 뺀다(`01_basic_design.md` §3.8.1).
- 비로그인 상태에서 담긴 장바구니는 로그인하면 계정 장바구니로 합쳐진다. 옮기는 동작은 쿠팡에 맡긴다.

### 12.7 실패 처리

`01_basic_design.md` §3.8.2를 따른다. 재시도 없이 품목별 성공·실패를 나누어 점주에게 수동 처리 안내를 표시한다.

확장 고유의 실패 사유를 아래로 구분한다.

| 사유 | 처리 |
|---|---|
| 확장 미설치·비활성 | 담기 버튼을 비활성화하고 설치 안내를 표시한다 |
| 검색 결과 0건 | 해당 품목을 실패로 두고 쿠팡 검색 링크를 제공한다 |
| `automate/match` 429 `ORDER_LLM_QUOTA_EXCEEDED` | 검색 품목을 실패로 두고 연결 상품 품목만 담는다. 실패 품목은 수동 처리 안내 |
| `automate/match` 422 `ORDER_LLM_GUARD_REJECTED` | 확장에 '요청이 거부되었습니다'와 `detail.reason`을 일반 텍스트로 표시한다. 검색 품목을 실패로 두고 연결 상품 품목만 담는다 |
