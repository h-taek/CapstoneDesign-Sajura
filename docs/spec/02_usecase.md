## 3. UC-01 회원가입

### 목적

점주가 사주라 서비스를 사용하기 위한 계정과 매장, 초기 운영 데이터를 등록한다.

### 사전 조건

- 사용자는 Google, 카카오 또는 이메일/비밀번호 방식으로 가입할 수 있다.

### 기본 흐름

1. 사용자가 Google, 카카오 또는 이메일/비밀번호 방식으로 회원가입을 시작한다.
2. 소셜 로그인인 경우 Frontend가 Backend의 OAuth 인가 URL로 이동한다.
3. Backend가 OAuth 콜백에서 사용자 정보를 조회한다.
4. 이메일/비밀번호 가입인 경우 Backend가 비밀번호를 해시하여 사용자 정보를 저장한다.
5. Backend가 회원 존재 여부를 확인하고 신규 사용자 정보를 저장한다.
6. Backend가 자체 JWT Access Token과 Refresh Token을 발급한다.
7. (사업자 검증 게이트 — 온보딩과 분리) 사용자가 사업자등록번호와 사업자등록증 파일을 입력한다.
8. Backend가 국세청 API로 계속사업자 여부를 검증하고, 통과 시 등록증 파일을 저장한 뒤 `business_status=PENDING`으로 둔다. 입력값이 마스터 코드면 호출 없이 곧바로 `VERIFIED`. `PENDING`·`VERIFIED`부터 온보딩 진입이 허용된다(승인 대기 중에도 진행 가능).
8a. (비동기) 관리자(`role=ADMIN`)가 `/admin` 심사 큐에서 등록증을 확인해 승인(`VERIFIED`) 또는 반려(`REJECTED`+사유)한다. 반려 시 사용자는 재검증한다.
9. 사용자가 매장명, 업종, 연락처, 주소, 매장 규모 구간, 운영 형태를 입력한다.
10. Backend가 매장 정보를 DB에 저장한다.
11. 사용자가 POS 연동 정보를 입력하고 연동을 시도한다. [POS API 연동은 2단계 — MVP는 CSV 모드로 진입]
12. POS API 연동 성공 시 `pos_mode`를 `api`로 설정한다. [2단계]
13. POS API 미연동 또는 연동 실패 시 사용자가 CSV 모드를 선택하며, 이 경우 `pos_mode`를 `csv`로 설정한다. (MVP 기본 경로)
14. 사용자가 초기 재고를 입력한다.
15. Backend가 초기 재고를 DB에 저장한다.
16. 사용자가 초기 메뉴와 레시피를 입력한다.
17. Backend가 메뉴와 레시피를 DB에 저장한다.
18. Backend가 온보딩 완료 상태를 저장한다.
19. Frontend가 메인 화면을 제공한다.

### 대안 흐름

- 사업자등록번호 검증 결과가 휴업·폐업·미등록·형식오류이거나 관리자가 반려(`REJECTED`)하면 **계정을 삭제하지 않고 유지**한 채 사업자 검증 화면에 머무르며, 미등록/형식은 재입력을, 휴업/폐업·반려는 사유를 안내한다. `UNVERIFIED`·`REJECTED` 상태에서는 온보딩으로 넘어가지 못한다(PENDING부터 허용).
- POS API 미연동·연동 실패 시 CSV 모드로 진행한다. CSV 모드에서도 수요예측·자동발주 추천 기능은 동일하게 동작한다 (`mvp_scope.md` §3·§6 데모 시나리오 기준).
- 온보딩 도중 이탈한 사용자는 다음 로그인 시 `onboarding_completed: false` 상태로 기존 단계부터 재진입한다.

### 사후 조건

- 점주, 매장 정보, 초기 재고, 초기 메뉴, POS 연동 상태, 온보딩 완료 여부가 저장된다.

## 4. UC-02 재고 관리

### 목적

점주가 식자재 재고를 등록, 수정, 조회하고 폐기 처리한다.

### 사전 조건

- 점주가 로그인되어 있다.
- 재고관리 또는 재고품목 정보가 존재하거나 등록 가능해야 한다.

### 기본 흐름

1. 점주가 재고 관리 화면에 진입한다.
2. Frontend가 재고 목록을 요청한다.
3. Backend가 DB에서 재고를 조회한다.
4. Backend가 재고 목록을 Frontend에 반환한다.
5. Frontend가 재고 목록을 표시한다.

### 등록 흐름

1. 점주가 재고 정보를 입력한다.
2. Frontend가 등록 요청을 보낸다.
3. Backend가 재고를 DB에 저장한다.
4. Frontend가 결과를 표시한다.

### 수정 흐름

1. 점주가 재고 수정을 요청한다.
2. Backend가 기존 재고를 조회한다.
3. Backend가 재고 수정 내용을 DB에 반영한다.
4. Frontend가 결과를 표시한다.

### 폐기 흐름

1. 점주가 폐기 요청을 입력한다.
2. Backend가 현재 재고 수량을 조회한다.
3. 폐기 가능 수량이 충분한 경우 Backend가 재고를 차감한다.
4. 수량 부족 또는 조건 불충분 시 Backend가 오류를 반환한다.

### 사후 조건

- 재고품목의 현재수량이 최신 상태로 반영된다.

## 5. UC-03 판매 데이터 조회

### 목적

점주가 기간별 판매 데이터를 조회한다.

### 사전 조건

- 점주가 로그인되어 있다.
- POS 연동 또는 CSV 업로드를 통해 판매데이터가 저장되어 있다.

### 기본 흐름

1. 점주가 판매 데이터 조회 화면에 진입한다.
2. 점주가 조회 기간을 선택한다.
3. Frontend가 판매 데이터 요청을 Backend에 보낸다.
4. Backend가 DB에서 기간별 판매 데이터를 조회한다.
5. Backend가 목록을 Frontend에 반환한다.
6. Frontend가 판매 목록을 표시한다.

### 상세 조회 흐름

1. 점주가 특정 판매 데이터를 선택한다.
2. Frontend가 상세 조회를 요청한다.
3. Backend가 DB에서 상세 정보를 조회한다.
4. Frontend가 상세 정보를 표시한다.

## 6. UC-04 메뉴 관리

### 목적

점주가 판매 메뉴와 레시피를 관리한다.

### 사전 조건

- 점주가 로그인되어 있다.

### 기본 흐름

1. 점주가 메뉴 관리 화면에 진입한다.
2. Frontend가 메뉴 목록을 요청한다.
3. Backend가 DB에서 메뉴를 조회한다.
4. Frontend가 메뉴 목록을 표시한다.

### 등록 흐름

1. 점주가 메뉴 정보를 입력한다.
2. Backend가 메뉴명 중복 여부를 확인한다.
3. 중복이 없으면 메뉴를 저장한다.
4. 레시피 입력이 있으면 레시피를 저장한다.
5. 중복이 있으면 오류를 반환한다.

### 수정 흐름

1. 점주가 메뉴 수정을 요청한다.
2. Backend가 메뉴를 조회하고 수정 내용을 반영한다.
3. 레시피 수정이 있으면 레시피를 수정한다.

### 삭제 흐름

1. 점주가 메뉴 삭제를 요청한다.
2. Backend가 메뉴의 소유권과 현재 삭제 여부를 확인한다.
3. Backend가 메뉴에 `is_deleted=true`, `deleted_at=현재시각`을 기록한다.
4. Backend가 운영 메뉴 목록에서 해당 메뉴를 제외한다.
5. 과거 판매 데이터는 기존 `menu_id` 참조를 유지한다.

## 7. UC-05 수요예측 관리

### 목적

점주가 메뉴별 1-3일 예상 수요 및 추천발주량을 확인한다.

### 사전 조건

- POS 판매 데이터가 존재한다.
- AI예측시스템이 예측 결과를 생성했거나 직접 호출 가능해야 한다.

### 기본 흐름

1. 점주가 수요 예측 화면에 진입한다.
2. 점주가 기간을 설정한다.
3. Frontend가 예측 결과를 요청한다.
4. Backend가 DB에서 저장된 수요예측 결과를 조회한다.
5. 결과가 존재하면 Backend가 바로 반환한다.
6. 결과가 없으면 Backend는 수동 실행 가능 여부를 확인한다.
7. 수동 실행이 요청된 경우 Backend가 AI Server를 호출하여 단건 예측을 수행할 수 있다.
8. 정기 배치 예측은 n8n이 DB/API 데이터를 수집, 전처리, 정규화하고 AI Server를 호출한 뒤 결과를 DB에 저장한다.
9. Frontend가 예측 결과와 예측 근거(산출 방법·출력 형태는 별도 확정)를 표시한다.

### 예외 흐름

- POS 연동 실패 시 예측 불가.
- 신메뉴 출시 직후 또는 특수 행사 등 모델이 학습하지 못한 변수는 예측 신뢰도 낮음으로 표시한다.

## 8. UC-06 발주 요청

### 목적

점주가 AI 추천발주안을 확인, 수정, 승인하고 쿠팡 장바구니 자동 담기를 수행한다.

### 사전 조건

- 추천발주 결과는 n8n 배치 워크플로우를 통해 DB에 사전 저장되어 있어야 한다.
- 점주가 로그인되어 있다.

### 기본 흐름

1. 점주가 발주 요청 화면에 진입한다.
2. Frontend가 추천안을 요청한다.
3. Backend가 DB에서 추천발주를 조회한다.
4. Frontend가 추천안을 표시한다.
5. 점주가 추천안을 확인한다.
6. 점주가 발주를 확정한다.
7. Backend가 발주 내역을 DB에 저장한다.
8. Backend가 Playwright에 쿠팡 장바구니 자동 담기를 요청한다.
9. Playwright가 쿠팡 장바구니에 발주 목록을 자동 추가한다.
10. Backend가 쿠팡 결제 진행 안내를 반환한다.
11. Frontend가 사용자에게 쿠팡에서 결제 진행 안내를 표시한다.

### 대안 흐름

- 점주가 수량 또는 상품을 수정하면 Backend가 수정안을 저장한다.
- 점주가 추천을 거부하거나 수정한 경우 해당 패턴을 다음 추천에 반영한다.

### 사후 조건

- 발주 내역이 저장된다.
- 장바구니 자동 담기 결과가 반환된다.
- 실제 결제는 쿠팡에서 진행된다.
